Training a model from the hub

Train on the project page: the training loop (v1.28)

The team's workflow is one loop per project (CONTRACT §41, U50): add items → label / correct → Train → the new model pre-labels every item that still has no human label → repeat. There is no pool or sampling step, and no form to fill: Train is one button with a fixed recipe. An iteration whose model is good enough is deployed automatically (U51).

What one Train does (the fixed recipe)

  • One iteration = one job of the template hub_loop with its default parameters (plus the project's Automation… › Training loop overrides), trained on the project's target ROIs in the project's modality (start.modality = the project's CT or MR, whatever the settings say — the executor otherwise defaults to CT; a sampler round's job gets it when its policy names none); the job's own pre-label hand-off (prelabel.hub_push) is off, whatever the settings say (pre-labels come from the step below); the trainer image is always pushed so the GPU cluster can run it. The model is filed under the project's model name everywhere — the strip, the Models pages, the app's model list — and shows Model <name> iteration <n> until it is deployed and gets a version (§41.10).
  • How long it trains (v1.38 §53, U69, 2026-10-20): the defaults are Oncostudio-Research's own — the executor reads TrainingConfig from the pinned Research clone (configs/training_config.py) instead of carrying values of its own, so a Research update changes them with it. At the pin (767b753, unchanged from 1ef108b) that is train.num_train_epochs 1000, a patch validation every epoch (train.eval_interval 1 — the best model is picked from these), a full sliding-window validation every 50 epochs (train.full_eval_interval 50), early stopping after two full validations in a row without improvement (train.full_eval_patience 2), 8 data-loader workers, AdamWConfig (its own learning rate, 1e-4 at the pin) and LinearDecayLRConfig, mode 3d, 1 × RTX_A6000. Every parameter of GET /exec/v1/templates says where its default came from — source: "research" or "executor" — and the reply names the commit (research: {commit, path}). The executor's own are only what the cluster needs: train.n_gpus, train.gpu_model, train.push, the wait's wait.timeout_hours (336 h = 14 days, since 1000 epochs at ALTJ's ~14 min each is ~10 days unless the early stop ends it) and wait.poll_seconds, and train.batch_size 2 (v1.39 §53.3, U88, D251 — 2026-10-21) for every template and mode: Research's 8 (3d; 32 for 2d) ran out of GPU memory on the RTX A6000 (47 GiB) for ALTJ jobs 62 and 66 and Thoracic_LN job 65; you may raise it. Each has its reason in the help. A value changed on the Parameters step reaches the generated training_config.py; an unchanged one is Research's. Before (job 61), the executor's own 200 epochs, Adam, batch 2 and 4 workers ran, and until U68 a full validation after every epoch.
  • 3D or 2D (v1.47 §63, U128, D292, 2026-10-27): train.mode (enum, options 2d, 3d in that order on every template, default 3d) is a parameter of hub_loop, hub_checkpoint, once and example. 2d runs the pinned pipeline's own 2d training — TrainingConfig(mode='2d') picks the Auto2DDefault network, the 2d loss and 512 × 512 slice patches (32 per volume) — and the batch size becomes the 2d default, 16 since v1.48 (§68; 32, the pipeline's own 2d value, under v1.47), unless the request sets one (3d stays at the cluster's 2, §53.3; a CUDA out-of-memory still halves it, §48.2). On hub_checkpoint, which trains nothing, it names the type of the checkpoint being evaluated. A mode the pinned pipeline cannot train is refused when the job is created (422 mode_unsupported, train.mode 2d: the pinned pipeline (…) cannot train 2d models), never mid-run. The job's model_type travels to the hub (events, model and deploy registrations), which names the family <CODE>_<type>.
  • 2d defaults load with the model type (v1.48 §68, U130-3, D300, E18): a parameter whose default depends on the mode carries default_by_mode: {"2d": …, "3d": …} in GET /exec/v1/templates (keys = the template's train.mode options; default stays the default mode's value). Today that is train.batch_size: 3d 2 / 2d 16, both executor values for this cluster (source: executor). The 16 is the user's value; it overrides Research's 2d rule of 32 as §53.3's 2 overrides its 3d 8. Nothing else in the pin's parameters depends on the mode: the 2d network, loss and 512 × 512 patch follow from mode='2d' inside TrainingConfig and are not parameters. A request that sets train.mode and leaves the parameter out gets the mode's value. GET /exec/v1/jobs/{id} then says so in params_changed: {"train.batch_size": {value: 16, reason: "mode_default", mode: "2d"}} (an out-of-memory retry, §48.2, replaces it with reason: "cuda_oom"). A batch size the request sets always wins.
  • The hub applies the model type's defaults (v1.48 §68, S36, D300): the wizard's …/train-default/preview and its submit, and the loop's Train, give every parameter with a default_by_mode the chosen type's value unless the user typed one (in this body, or in the loop's policy) or the pipeline sets it — an admin's recipe value stands. The value is sent with the job, so params_changed shows it (2d: train.batch_size: 16, from 2) and the job page lists it as a change. The preview also lists the type's defaults as defaults_for_mode (2d: {train.batch_size: 16}, 3d: {train.batch_size: 2}); params keeps each entry's default_by_mode so the page can reload the field when the type changes (W22). An executor without default_by_mode gives an empty defaults_for_mode and changes nothing.

  • Which labels: per image series the newest human label as of the press whose state is one of the project's labels to train on (v1.29 §42.4, setting loop_label_states) — by default all four human states, approved, unreviewed, changes requested, legacy, so not-approved labels train as well; a lead narrows it on the training view or in Automation… (e.g. approved only: then an item whose newest label is unreviewed trains on its newest approved label, if it has one, else not at all). Only the project's own labels (v1.31 §44, U54): a label saved for another project on the same image series does not count, does not train and does not make the item labeled here — such an item gets this project's pre-label like any unlabeled one. Own = delivered or corrected on one of this project's items (or saved with one of them named), an Excel-era label of a series this project's workbook imported, and — where the hub cannot tell (an early save that names no item, or whose item was re-created) — the projects that hold the series. The same rule holds for every count on the strip, the training view, the wizard's cards and cohort preview and the Default pipeline. An AI pre-label never enters; items without an image series are skipped. A label whose file exists nowhere — neither saved to the hub by the app (v1.20 and later) nor on the PACS (an Excel-era or sent label) — is skipped too and not counted (§41.9): the strip's count is of usable labels, and the project's Iterations… lists the skipped items with label file not found on the hub or the PACS; relabel them in OncoStudio to bring them back. An Excel-era row whose only label is a hub-built merged record (v1.33 §47: a record, no file) trains from the one RTSTRUCT on the PACS that holds every target ROI — or every ROI picked in the wizard's Target ROIs step, so a smaller pick can make more rows usable. It counts as a legacy label. When the ROIs sit in two or more RTSTRUCTs, or one is in none, the row is skipped and Iterations… says target ROIs spread over 2 structure sets or missing target ROIs: <list>. A label saved in OncoStudio always wins over the merged record.
  • Validation set: at the project's first Train the hub freezes it — the rows a lead marked valid when there are any, else max(5, 15 % of the labeled patients) patients drawn stratified over the usable labeled items' facets (sex, age, vendor, thickness, …). Every later Train evaluates on the same items, so DSC values are comparable across iterations. Only an admin replaces it (reset). A validation item without a label blocks Train (2 validation items are not labeled yet).
  • Minimum: 10 labeled items (setting min_labels; never fewer than twice the validation minimum), counted in the chosen states — with approved only, label at least 10 items first (4 labeled) counts the 4 approved ones. The validation draw at the first Train is over those labels too, and a validation item counts as labeled only with a label in the chosen states.

Pre-labels after every iteration

As soon as the job has exported its model (before evaluation), the hub starts one prelabel_only job for every item with an image series, no human label and not in the validation set (≤ 500 per job; more follow one job after the other). OncoStudio pulls each pre-label when the item is opened and shows it as AI_PRELABEL; the labeler's save replaces it. While the project has a model and auto pre-label is on, items added later get a pre-label from the current model within 10 minutes (the hub's round tick batches them into one job). An item with a human label never gets a pre-label, and a series is pre-labeled once per model.

Automatic deploy

When the evaluation is in, the hub compares the mean DSC over the validation set (the mean of the per-ROI means) with the project's deploy_threshold (0.85 by default). At or above it, and once the job has ended, the hub deploys the model to /mnt/deploy/models/<model name>/<next version> — the family's highest version plus one patch, 1.0.0 for a new family — with the memo auto-deploy: project <code> iteration <n>, DSC <x> on <v> validation items, job <id>. An iteration deploys at most once. The deployed model is registered by the next sync_deploy run, so it appears in the app's Auto-contour… model picker and ai-pipeline evaluates it. Below the threshold nothing is deployed; a lead may still deploy from the job page (Deploy; since v1.38 the version and the memo are prefilled). A failed deploy shows its reason. v1.38 §55: when the loop's pipeline (below) deploys (deploy.enabled on, as the seeded Default does), the iteration's job deploys itself instead — its Deploy to the server stage runs after Evaluate with the next version and the memo loop: project <code> iteration <n> · by <presser>, whatever the DSC, at most once; the strip says deploying while that stage runs and deployed / failed from its end, and the threshold deploy above does not run for that iteration.

Training: Dashboard and the Training wizard

Menu. The Training group has two entries: Dashboard and Training. Models, Datasets, Evaluations, Releases, Run records, ROI registry, Reconciliation and Pipeline are not in the menu; their pages open from the links on the job, model and run pages.

Dashboard (/training) shows the counts (running, queued, succeeded and failed in the last 7 days, the latest DSC), a card per running or queued job with its stage bar, and the finished jobs. You can filter them by state, search by project, template, person or number, and tick Mine only; each row has its DSC and model. New training opens the wizard. Every project name is a link to the project's progress view (v1.49 §67.1, below).

How the Training pages stay current (v1.39 §57). Each page fetches on its own schedule, and only while something on it is live. The Dashboard asks for the job list every 15 s while a job runs or waits; with nothing live it asks for nothing. A job page asks every 10 s while its job is live. A live event never adds a fetch: it only brings the next one forward, at the earliest 2 s after the last, so a busy job costs no more requests. The state chips and the search filter the list on the page; only ticking Mine only asks the hub again. A reload that brings the same data changes nothing on screen, and no reload shows a placeholder. A failed reload keeps the page as it was. The job page fetches the loss curve and the evaluation again only when a stage changes state, and adds new log lines to the end of the log. On a project page, while the loop's job runs, only the loop strip refreshes every 10 s; the table keeps its own pace and reloads once when the run ends. The wizard asks for each of its project's lists once when it opens, and the Parameters & submit step reloads its project only when that project's labels change; a reload that brings the same data changes nothing. Its preview is asked again only when something you set changes (project, pipeline, items, ROIs, parameters, deploy). A job's progress anywhere only re-checks the preview (a running job of the project blocks Submit), at most once every 15 s. The project page's periodic reloads change nothing on screen when the data is the same (U78).

Evaluation and metrics

A job's evaluate stage produces the executor's own quick check (a metrics.csv on the job page). The figures that count for a release and for regulatory documents are computed once a model version is deployed, by ai-pipeline's calculator on each data version's validation cases, and registered in the hub:

  1. Deploy triggers it. When the hub's change feed announces a new model or data version, ai-pipeline queues a standard evaluation (the model on its family's latest data, or new data with the latest model). It waits for free memory and the shared GPU lock, so it never competes with a running training stage. A lead can also queue a pair in ai-pipeline's 추론 관리.
  2. Leaked cases are left out. Validation cases the model trained on (same DICOM series, or identical image content) are skipped and listed as excluded; the training split comes from the hub's record of the job that produced the weights. Label states (§6.12) do not change what is scored.
  3. Aggregated by ai-pipeline, never by the hub. Per ROI: mean and median DSC and HD95 and n (POST /svc/v1/evaluations, §3), plus one row per case and ROI (…/{id}/cases) for drill-down. The hub shows the figures in 평가 and on the model and job pages exactly as sent.
  4. Case facets on the way. While scoring, the calculator also records each case's scanner model, modality, study date, spacings and institution from the same DICOM header (v1.5); ai-pipeline passes the exactly identified series to the hub's labeling pool (Rounds › facets). Demographics the header cannot give (NIfTI-only public data, cases not on the central PACS) are filled from ai-pipeline's case metadata registry (/mnt/deploy/config/case_meta), each with its source in the result's meta_sources; the 인허가 프로파일 counts them apart from header values (값 출처). A header read from a non-image object (an RTSTRUCT that is the only file of a case folder) gives sex, age and study date only — its manufacturer is the software that wrote it, not the scanner — and the calculator then reads the image's header from the central SCP. For MR series it also records T1/T2 weighting, contrast and field strength (the 인허가 프로파일 workbook's 영상종류 rows). GT volumes (volume, ml per ROI) come from the metric's own per-label GT voxel counts × voxel size, the same channel mapping as the DSC; results written before 2026-10-15 can hold misnamed or zero volumes, which readers ignore.
  5. Regulatory criteria. The 인허가 프로파일 judges each ROI by its mean GT volume — DSC ≥ 0.5 / 0.65 / 0.8 for < 10 cc / 10–150 cc / ≥ 150 cc (95%HD reported, not judged), with CT and MR apart and the 기준 미달 rows carrying diagnostics and a 조치 record (ai-pipeline › Profiles).
  6. Keys. An evaluation is identified by model family and version, data version and the training split's split_hash (unknown for historical results whose split may have been rewritten since). Registering the same key again replaces it; hiding the model version withdraws it.

The viewer on the job page (v1.39 §56.3). Once a job's evaluate stage has succeeded, its Evaluation card spans the page width and shows a Viewer under the tables (a job imported from the old aitw has none). On the left are the validation cases: each shows its id, its overall DSC (the mean over the classes) and one coloured chip per class with that class's DSC. Clicking a case opens it, and so does clicking one of its rows in Per case. The centre shows one slice, with the CT image and the overlays drawn on top:

  • GT and Prediction switch the two overlays on and off. With both on, GT is drawn as an outline over the filled prediction (both use the same class colours, so two fills could not be told apart); either one alone is filled. Opacity sets how strong the fill is (0.45 by default). Click a class in the legend under the slice to hide it, and click again to show it.
  • Changing the slice: use the slider, the mouse wheel over the image, or, after clicking the image, ↑ / ↓ (one slice), PgUp / PgDn (ten slices) and Home / End (the first / last slice). Beside the slider: k / n (counted from 1) and the slice's distance in mm from the first slice.
  • Plane (Axial, plus Sagittal / Coronal when the executor serves them) opens the new plane at its middle slice. Window (CT only): Soft tissue (400/40, the default), Lung or Bone. MR images are scaled to the 1st–99th percentile of each volume.

Every clicked case renders; what the viewer is doing (v1.45 §56.4, U115). The slice you asked for is always fetched first: changing the case, the plane or the window stops what was still loading for the old one, the slice number is kept inside the new case's slices, and the five slices on each side are fetched only once the current one is drawn (in at most three of the browser's six connections, so a click never waits behind them). A slice that is still on its way after one second shows Rendering… over the previous picture, dimmed — the first look at a case whose image the executor has not read yet can take tens of seconds. A slice that the hub could not deliver is asked once more; if that fails too the picture says Could not load slice k (status) (for example 502 when the executor took longer than the hub waits) and the previous picture stays; moving the slider asks again. Cases the report prerendered (Prerendered evaluation samples) carry a ready chip, are listed first and the first of them opens when the address names no case. The parameter's title and its lower bound show in the Parameters step and in 관리 › Pipelines (group Evaluation report).

The case, slice and plane go into the address (?case=&slice=&plane=), so a copied link opens the same picture. Nothing is kept in the browser's storage. The case is the executor's case number, the slice number in the address starts at 0, and axial is left out of the address. The list and the slices are loaded once per evaluate result and are not polled. If the run's files were cleaned up, the card says the images are gone and keeps its numbers.
