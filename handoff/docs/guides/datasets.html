Datasets, splits and their provenance

After this page you can read a dataset version page, tell where each sample and its label came from and in what state, compare train and valid demographics, and export the profile.

Last verified 2026-10-01 · CONTRACT v1.7 · owner: labeling-server, labeling-web

What a dataset version is

A dataset version is one train/valid split of one model family, identified by model_family × split_hash (the hash covers role, sample, image series, RTSTRUCT series and image checksum — provenance). It arrives from three places: the executor when a training job builds its split (source=aitw), sync_deploy from the data folders under /mnt/deploy (deploy), and the Excel import (excel). Samples whose image series could not be matched exactly are marked inferred (one known series for that patient) or unresolved.

The dataset page (데이터셋)

  • Header: family, data version, source, split hash, train/valid counts, the run and the models trained on it.
  • Label states strip (v1.4): how many samples were approved, unreviewed, changes requested, AI pre-labels or legacy when the split was drawn, and the cohort request (states, time). Splits registered before v1.4 show unknown.
  • Demographics per role (sex, age, vendor, scanner, slice thickness, contrast, …) with the source mix of each field; profile.xlsx exports the same figures (display only — regulatory figures come from ai-pipeline).
  • The sample table: role, patient (masked for viewers), series, resolution, label state, projects, labeler, revision time (and a warning when a newer revision exists), review verdict, image checksum, metrics.
  • v1.60 §76.3 (U151, D329): labelers read the dataset, model, evaluation, release and run pages (GET /ui/api/registry/datasets[/{id}], models[/{md5}], evaluations, releases, runs[/{run_id}]) exactly as a viewer does, patient IDs included (U5); the profile.xlsx exports and the reconciliation stay lead / viewer / admin (data scope), adding an ROI by hand stays lead / admin.
  • v1.61 §77.4 (S52, D333): 릴리스 (GET /ui/api/registry/releases) lists every registered bundle with its state — candidate, released, superseded, withdrawn from the bundle's RELEASE.json, released for an older x.y.z bundle registered without one, none for a four-part bundle not yet registered with one — plus base version, bump, notes summary, Jira keys, creator, release time, and latest_released: the newest bundle of the released channel. A model counts as released (here, in OncoStudio's model list and on the roadmap) only through a released bundle; a candidate's models are not.

Label states in a split

The training wizard's state selection (or a policy's label_states) goes to the executor with the job; the executor draws the cohort from label-set and registers the split with each item's label_state (see below). To answer "was this model trained on unreviewed data?": open the model page → its training split → the label-state strip and column. Services ask the same through GET /svc/v1/models/{md5}/training-split, whose items always carry label_state (unknown for splits registered before v1.4, never omitted).

What the executor sends with a split

This section: executor (DOCMAP maps the executor's split registration here).

When a training job's split is ready, the executor registers it at the hub (POST /svc/v1/splits, CONTRACT §3, §6.12). What it carries depends on where the job's cohort came from:

Cohort fromEach itemThe split
label-set (hub v1.4)label_state (approved, unreviewed, changes_requested, prelabel, legacy) and label_kind (human, prelabel, historical) of the RTSTRUCT that was trained onlabel_states — counts per state — and cohort: the time the states were judged at, the states asked for, the project, the policy when a policy started it
approved-set (older hub)no label fields (an older hub refuses unknown fields)no label fields; the hub shows these items as unknown

A split registered from a job with a frozen validation set (valid_pinned, §11.6) has exactly the pinned series as its valid items; the hash is computed the same way, so the same items give the same hash whether they were pinned or drawn.

The model's type (v1.47 §63). The model registration (POST /svc/v1/models) and the model deploy (POST /svc/v1/deploys) carry model_type (3d | 2d) — the job's train.mode — when the hub reports contract 1.47 or later; the split and the run registration are unchanged.

The run's training curve (v1.48 §66, E17). The run registration's metrics_summary.curve (§8) is the job's curve rows, [{epoch, train_loss, valid_loss, valid_dsc, full_valid_dsc?}]: full_valid_dsc only on the epochs where the trainer's full (sliding-window) validation ran (every train.full_eval_interval, 50 by default). Beside it, metrics_summary.best = {epoch, full_valid_dsc} (the first epoch with the highest full validation, the one the trainer kept as best_full_model.pth) and metrics_summary.stop_reason (early_stopping | epoch_limit | manual_stop). The full-validation values come from the trainer's TensorBoard file in the experiment folder (full_eval/dice_mean, mapped to epochs through training_log.json's steps): training_log.json keeps only the running best, so the evaluations that did not improve are nowhere else on disk. Without the event file, only the improving epochs are listed. Long curves are thinned to 500 points, but full-validation rows are always kept. Job 79 (81d49984): 9 values, 50 … 450; best 0.8539 at epoch 350; early_stopping.

When the split arrives. Each item's image_sha256 (of the decompressed image) is computed after the split stage, in the executor's background sender, at roughly 0.7 s per image and cached per file — so a 100-case split reaches the hub a minute or two after the job's split stage shows done, while the job goes on. Each hash is saved the moment it is computed (since 2026-10-18), so the hashing never holds up the job's own stages.

Validation entries marked by hand (v1.7). Besides the set the round sampler freezes at round 1's commit, a lead can mark a project's cases valid or train from OncoStudio's project page (CONTRACT §13 split). Those entries live in the same labeling_project.valid_set.series (listed again in manual_series, with manual:true and frozen_at set on the first add), so every later training job pins them too (valid_pinned), the auto-train gate waits for their labels and a pre-label request for them is refused. The sampler treats them as frozen: it draws no second validation set while the set is non-empty, the leak guard holds their patients out of every sample, and a round reset releases only the series that round's sampler froze. A series that already has a pre-label cannot become valid (§11.4); a sampler-frozen series leaves the set only on an explicit train mark by a lead; the admin reset on the Rounds tab clears everything.

The split hash does not change with label states (D75): it names the role, sample, image series, RTSTRUCT series and image checksum, and the state is information about that RTSTRUCT. The file the pipeline trains from (train_valid_dict.json) is the same format either way.

Demographics and reconciliation

Each sample's demographics come from the case metadata first (DICOM headers, C-FIND, OncoStudio events), then from ai-pipeline's per-sample values for deployed splits whose series are not in the hub (D49); the page shows which source each field used. 인구통계 대조 (reconcile) puts the hub's profile of a deployed data version next to ai-pipeline's regulatory profile, in ai-pipeline's categories and counting rules, and flags differences of 5 percentage points or more over patients with a known value; categories the hub has no values for are marked, not flagged.

From a split to models and evaluations

Dataset → the runs trained on it → their models (weights md5) → evaluations of each model on each data version → releases that shipped those models. Every page links the next: dataset page → model chips; model page → training split, evaluations, releases, deploys, flags; run page → dataset and models; job page → run, dataset, models. Since v1.13 the 모델 list also says, per set of weights, which projects and ROIs the training job used and the mean DSC of its evaluations — the same three fields OncoStudio's Models tab shows (GET /api/v1/models, §21.1). Since v1.16 (D142) a model is one row: its newest version (numeric order, 2.0.10 after 2.0.9), the version in a release, how many versions exist, and the newest version's projects, ROIs, DSC and date; click the row for every version, newest first, and a version for its page. The app's Models tab groups the same way. Since v1.21 (§28.1, D168) released means the version shipped in the newest release (the highest numbered one; site builds such as smu_* are not releases) — MR_HNN's newest is 2.2.0 while 1.7.0 ships 2.1.0 — and a model hidden in /mnt/deploy/config/hidden_models.json (the whole family, or one version) is marked hidden rather than left out; the hub ranks the families once (families[] of GET /api/v1/models) so the auto-contour picker and the Models tab agree. Since v1.36 (§50) an admin also hides models, ROIs and one model's ROIs on the hub (관리 › Hidden). The hidden set is the hub's entries plus that file. A hidden family or version is marked hidden in the model list, so pickers leave it out. Each model lists the ROIs hidden for it (rois_hidden). A hidden ROI drops out of the ROI registry pickers (GET /ui/api/registry/roi, GET /api/v1/roi/registry; both name it in hidden[]), and the roi-board no longer counts it as held by any model. The page 관리 › Hidden (admins only; others get Admin only) has three tabs — Models (families, each with its versions), ROIs (the registry) and Model ROIs (each family's newest model's ROIs) — with the hidden ones first, a search and Hidden only. Hide… asks for an optional note and hides at once; Unhide makes it visible again. ai-pipeline's entries say Hidden by ai-pipeline and cannot be changed here (edit the file). The model lists follow right away: a hidden family leaves Labeling › Models and every picker. Since v1.37 (USER 2026-10-20) the set also takes projects and project-only ROI names. A hidden project stays labelable (unlike archiving) but puts nothing on the roi-board — none of its targets, labels, dates or jobs, and no projects in progress entry — and is left out of the public overview; GET /ui/api/projects and the project page mark it hidden. A hidden ROI now also leaves the roi-board while an open project lists it as a target. The ROIs tab can offer the target names outside the registry (targets), hidden as written. On the page (hub 1.37 or newer) a fourth tab Projects lists every project that is not deleted — code (a link to its page), name, modality and status when not active — with the same search, Hidden only, Hide… (an optional note; the dialog says the project stays labelable and leaves the roadmap, Projects in progress and the public overview) and Unhide; a hidden project shows a hidden badge on Projects and in its page title. The ROIs tab lists the target names no registry entry maps after the registry's names, each marked project target with the projects that list it; hiding one takes it off the roadmap although those projects stay open, and they keep it as a target.

ROI names typed by hand (v1.39 §45.4)

The ROI registry is ai-pipeline's roi_names.csv, mirrored by the hub. When the wizard's From scratch picker gets a name that is in neither its official names nor its alternative names, a lead can add it: POST /ui/api/registry/rois {name, modality?} (lead or admin). The name is trimmed and compared like every ROI name (case and spaces ignored). An official name or an alternative name answers 200 {official, created: false} with the registry's spelling, so a second entry cannot be made by spelling. Anything else is stored as the hub's own ROI (table roi_custom: name as typed, modality, who, when) → 201 {official: name, created: true}. An empty name, one over 100 characters or one with , | or a control character → 422, as is a modality other than CT or MR.

A custom ROI is part of the registry the hub serves. /svc/v1/roi/registry.json lists it as {official: name, aliases: [], source: "hub"} (the file's entries say source: "aipipeline"), and registry.csv has a row for it with no alternative names. The converter's alias table and the executor's official-name rule (§48) therefore know it with no change on their side. The pickers' source GET /ui/api/registry/roi marks it custom: true and lists every custom ROI with who added it under custom (관리 › ROIs). The hub never writes ai-pipeline's file. When the file later lists the same name, the entry becomes the file's (with the file's alternative names), and the roi_custom row stays as the record of who added it.

Alternative names added on the hub (v1.65 §80.1, U159, D339). A lead can give a registry or custom ROI an alternative name of the hub's own — in the training wizard by dragging a dataset's ROI name onto a target ROI: POST /ui/api/registry/aliases {official, alias} (lead or admin). 201 stores it (table roi_alias_hub: the alias as typed, the ROI, who, when); a name that already means that ROI answers 200 created: false; a ROI the registry does not know → 404 unknown ROI: …; a name that already means another ROI (its official name, one of its alternative names, a custom ROI) → 422 alias names another ROI: …. The alias is served with the registry at once — registry.json (aliases and hub_aliases), registry.csv (alternative_names), the pickers' source — and counts in every hub comparison of ROI names, in every project and job. DELETE /ui/api/registry/aliases/{official}/{alias} removes a hub alias; the file's own alternative names cannot be removed there (403 owned by the registry file). 관리 › ROIs lists the hub's aliases with who added them (GET /ui/api/registry/roi hub_aliases; GET /ui/api/registry/aliases?official= lists both kinds). When ai-pipeline's file later lists the same name, it is the file's.

Since v1.55 §72 (S47) GET /ui/api/registry/roi is part of the public set: every signed-in account (labelers too) and a visitor without a login read it — the roadmap's ROI picker uses it. An anonymous reply carries no names: custom[].created_by is null (app/ui/routes_registry.py roi, app/ui/auth.py blank_names).

What can go wrong

Many unresolved samplesDeployed splits name patients, not series; they resolve once the series is known to the hub (C-FIND/header sync) or ai-pipeline sends per-sample meta.
A version is not deployableai-pipeline's bundle validation failed (e.g. an image read error); see its validation page.
The same split twiceA split is keyed by its hash: re-registering the same content updates it; a changed item makes a new version.
Label states show "unknown"The split was registered before v1.4 or by an older executor; nothing is wrong with the data.
A project is missing from a split's project listit was deleted (v1.19 §13, D157): deleted projects are left out of the registry's project columns and lists; an admin can undelete it on the web.
