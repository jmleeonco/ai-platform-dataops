Deploying a trained model or dataset

After this page a lead can run a deploy from a job page safely: what the memo is for, why an existing version is refused, what a dry run shows, what lands under /mnt/deploy, and how to roll back.

Last verified 2026-10-20 · CONTRACT v1.38 · owner: ai-training-web

What deploy does

Deploying copies a finished job's result into the shared production folder /mnt/deploy, where products and ai-pipeline pick it up. There are two kinds:

KindWhat is writtenScript (unchanged research code)
modelthe exported weights (3d_final_model.pt) and its files into /mnt/deploy/models/<name>/<version>deploy/deploy_model.sh
datathe job's train/valid lists and their images into /mnt/deploy/data/<name>/<version>deploy/data_deploy.sh (run as a copy with its settings filled in; it never deletes the target folder first)
  • Who may deploy: hub roles lead and admin. Labelers and viewers are refused.
  • New versions only. A version that already exists is refused (deploy_version_exists): the model script would copy over a live version in place.
  • A memo is required (missing_memo otherwise). It is the only record of why something shipped.
  • The model name may contain only letters, digits and _ (the script's own rule, checked before anything runs).
  • A deploy from the job page is a stage of its own, run by the service account; it never waits behind, or blocks, the job's other stages.

A deploy inside the job (v1.38 §54, U70): the default pipeline (hub_loop) ends in a Deploy <name> <version> stage after the evaluation, when deploy.enabled is on. The hub fills the model name, the next version (editable in the wizard) and the memo (wizard: <name> · by <user>), so the same rules hold: a taken version or an empty name, version or memo is refused when the job is created, not after a day of training; the stage runs only if the evaluation and every stage before it succeeded; it records the same deploy as the button below. Off (the once template's default, or a loop job that names no model), the job has no deploy stage.

How to deploy from the hub

  1. Open the finished job (학습 › 작업 → the job) and choose 배포 (deploy).
  2. Pick the kind (model or data), then the name, the version, the modality (ct/mr) and, for a model, the ROIs to mark as research (one comma-separated list; empty = all released).
  3. Write the memo: what this is and why it ships.
  4. Leave dry run ticked first. The dry run shows the exact command that would run and the target folder, and checks that nothing would be overwritten — it writes nothing.
  5. Untick dry run to deploy for real. The deploy appears as a new stage on the job page with its own log.
Tests and acceptance never deploy for realOnly dry runs or scratch deploys (D67): /mnt/deploy is shared production.

Scratch deploys (dev): deploy_model.sh always writes /mnt/deploy/models and commits into the research repository, whatever folder the executor is told, so an executor started with AITW_DEPLOY_SCRATCH=<folder> does not run the scripts at all: a deploy stage copies the exported 3d_final_model.pt into <folder>/models/<name>/<version> with a deploy.json (memo, the command that was not run), and the stage log starts with [scratch deploy …] not run: sh deploy/deploy_model.sh …. Version checks look in that folder; the hub still gets the deploy record. The dev executor (:8901) runs this way; production never sets it.

What is recorded

Rollback and mistakes

  • Nothing is overwritten, so a bad deploy never replaces a good one: the previous version is still there and still what products use until someone points them at the new one.
  • To withdraw a version, retire it in ai-pipeline (model flags) or the release process — see the releases guide. Deleting from /mnt/deploy is a person's decision, never an automatic step.
  • A deploy that failed half-way leaves a partly written folder: its version counts as existing, so deploy again with the next version and ask whoever owns /mnt/deploy to remove the broken folder.

What can go wrong

"a memo is required"the memo was empty → write one; it is the only record of why.
"… already exists; deployed versions are never overwritten"that name/version is taken → choose a new version.
"only a lead or an admin may deploy"your hub role is labeler or viewer → ask a lead.
"job … has no exported model"the job did not reach its export stage, or was a data-only job → deploy a job that exported, or deploy the data kind.
The deploy stage waitsthe service lane or the target's lock is held by another stage → it starts when that finishes; the job page shows it queued.
Permission denied under /mnt/deploythe NFS export or folder ownership changed → an administrator fixes the share; nothing was overwritten.
