Releases: packaging, validation, registration

After this page you can package a release in ai-pipeline, validate its bundle, see it registered in the hub with its models and countries, and withdraw it if needed.

Last verified 2026-11-05 · CONTRACT v1.61 (§77: immutable packages; the rest v1.4) · owner: ai-pipeline, labeling-web

What a release is

A release is a named set of trained models shipped together, e.g. 1.7.0. On disk it is a folder /mnt/deploy/release/<version>/ with one sub-folder per model (weights 3d_final_model.pt and global_fingerprint.json) plus shared top-level files. Names of the form x.y.z are standard releases (the newest is the dashboard's LATEST); prefix_x.y.z are custom builds. A model sub-folder is named after its family, old names and hub-trained <CODE>_<3d|2d> (RIBS_3d, §63) alike; the model picker (/packaging/release-models) and the 모델 다운로드 page show each family's model_type (3d when the name has no suffix).

models[] = family, version, md5, input classeseach model folder; the version is the catalog version whose weights are byte-identical (md5), because a package's git_tag has been wrong before (1.6.4); else the declared tag; else unknown

Packaging and validating

All in ai-pipeline /packaging/ (모델 패키징); the actions that write are admin-only.

  1. Check the numbers first. /spec/package/<version> shows every model of a release with its evaluation (DSC/HD95 per ROI, leak-guard exclusions); /spec/compare compares two releases ROI by ROI. A model with no evaluation yet can be queued from 추론 관리.
  2. Check the data behind them. Every deployed data version is validated automatically after deploy (bundle validation, D37: class lists, GT channel count, empty channels, valid/valid_gt order); a failed validation is on /spec/validation/<model>/<data version> and marks the dataset not deployable in the hub. Model flags (duplicate weights, channel-swap suspects, D38) appear in the hub's model page.
  3. 새 패키지 (new package). Choose a name (x.y.z or prefix_x.y.z) and the model versions; the dialog shows the difference to an existing release before anything is written. Create writes /mnt/deploy/release/<name>/ (models + the shared files of the latest package). If the name exists you must confirm the overwrite; the old folder is moved to /mnt/deploy/trash/, not deleted.
  4. Permit 동기화. Pull the per-country ROI permits (KR, JP, US) from the certification sheet; the status strip shows how many ROIs each country allows. Each country reads one tab (PERMIT_SHEET_TABS: KR/JP …OncoStudio 2.1.x, US FDA_OncoStudio 2.2.x) — when RA renames or adds a version tab, update that map or the country fails to sync and keeps its old list. Digit-only cells are list numbers, never ROIs. The 인허가 프로파일's ?permit= filter reads the same lists.
  5. Build a package for a country. Pick 기준 릴리즈 (the release to start from), 새 버전 이름 (the output name), the country, modalities (MR/CT/GTV) and optionally single models. The build rewrites every model's usage list to the country's permitted ROIs and returns a zip. Nothing is written back into the release. The dashboard's download dialog builds the same way for everyone.

The hub's 배포 section (§70, U134) offers the same actions through ai-pipeline's JSON API (/api/v1/deploy/packaging…, proxied as /ui/api/deploy/packaging…) with the same functions and role rules: 새 패키지 options, diff and create; Permit 동기화; the permit CSVs; the per-model zips. A country build there is a background job (POST packaging/build → packaging/builds/{id} → the zip at packaging/download?job_id=), because a 2 GB bundle takes longer than the hub's 30 s request timeout. Details: ai-pipeline component page.

The coloured dot next to each model version on /packaging/ means: green, that version has /spec numbers (an evaluation); orange, only another version has; grey, none. Before 2026-10-29 every dot was grey, because the page read a Notion-era cache that no longer exists.

Config 관리 (/config) keeps the shared config files of a release (ROI presets, channel modifications, landmarks, the OD models) as git tags: vx.y.z for a package and vx.y.z.n for a sub-revision registered on top of it (1.7.0.1, 1.7.0.2). The latest badge is the highest of these by number; prefixed custom tags (vwsch_…, vsmu_…) are never latest (D318). Registering a tag changes no release folder: the copy into the deployed bundle (_deploy_to_release, which rewrote 1.7.0 in place and made D317 necessary) is gone since 2026-11-05 (D331).

Since 2026-11-05 a package never changes (CONTRACT v1.61 §77, D331–D333). A config, model or OD change becomes a new folder made with the hub's 배포 › 새 릴리즈 wizard. It is written by ai-pipeline's release writer, with RELEASE.json (state candidate → released → superseded, or withdrawn), RELEASE_NOTES.md and its own config tag. Latest on the dashboard and the hub is the highest released package; folders made before that date count as released, and 1.7.0.3 is a candidate until QA marks it released. A country build never includes RELEASE.json, because the state changes after the build. How to: the release flow; the API: ai-pipeline component page.

Registration in the hub

ai-pipeline registers releases itself; nobody types them into the hub.

Action in ai-pipelineWhat the hub receives
새 패키지 createdthe release with its models (POST /svc/v1/releases, §3)
새 패키지 over an existing namefirst a withdrawal of the old content (§6.3, reason "패키지 덮어쓰기"), then the new content — registering again un-withdraws it
Package build for a countrythe release again with that country added. A build named after an existing release registers that release's full model set, never the modality-filtered subset; a build under a new name registers the built bundle itself
A model version hidden in /admin/modelsits evaluations are withdrawn; releases are not changed

Countries (§6.4): the list ai-pipeline sends replaces the stored one; an empty list means "unknown" and never erases countries already recorded. Evaluations are registered separately per model version × data version (Training › Evaluation); the hub links a release's models to their evaluations by weights md5 and split_hash. If the hub is down, registrations wait in ai-pipeline's outbox and are sent when it is back; python3 scripts/hub_register.py status shows what is pending.

ROI roadmap: progress, schedule, requests

The hub's first page (ROI roadmap, /roadmap; the landing page for leads and admins, in every account's menu, labelers included — USER 2026-10-17) shows, for every ROI and modality, how far it is and when it is planned to come out.

  • Counts per stage (click one to filter): Released (a live release's model holds the ROI), Validating (a model holds it), Training (a hub job for it runs), Labeling (labeled items exist), Planned, On hold, Not started. The stage follows the data unless a lead sets it in the plan (the tooltip then names the stage the data says).
  • Sections (CONTRACT v1.35 §46.5, USER 2026-10-18 "actively working ROIs at the top"): the timeline and the table list the ROIs in three sections, each with a header and its count — Active first, then Planned / not started, then Released. Active = the stage is Labeling, Training or Validating, or a stage started or the plan changed within the last 30 days. A release date is not activity, and a released ROI counts as active only when a stage started more than a day after its release (new work on it, e.g. a training job): the 2026-09-28 registry import dated hundreds of releases, model validations and labels on the same day, which would otherwise fill Active with everything released. An ROI on hold stays under Planned / not started. The stage counts, the GTV / CT / MR filter and the search act within every section; a section left with no ROI keeps its header, greyed. Models marked hidden and closed projects put nothing on the board (the hub drops those rows).
  • Live, and projects in progress (CONTRACT v1.36 §49, USER 2026-10-19): the page refreshes itself in place when anything behind it changes — a job starts, moves to its next stage or ends, a label is saved or approved, a model or release is registered, a plan or request changes (the hub's live event roi_board; after a lost connection the board is fetched again; an account without the live stream, such as a labeler, refreshes every 60 s). Projects in progress, above the sections, has one card per project with a running or queued job or with labels in the last 7 days — the running job first: training · stage 7/11 · since 22:24 (opens the job), or 14 labels this week (opens the project's training page). In Active, ROIs with a running job come first, then the most recent change; such a row shows training now with a pulsing dot (a released ROI keeps its release: In release wsch_1.3.0 · v1.0.2 beside training now). Each card also lists its ROIs (v1.39 §49.1): the project's targets with its label count and target count, the ones its running job trains first. On the card they are chips Liver 20/30 (usable labels / the target count when set). The running job's ROIs carry a dot, and past six the card shows +n (hover for the names). A chip shows that ROI's row in the board below: it is scrolled to and marked for a moment. If the filters hid the row, they are cleared to a search for that ROI first (U81).
  • Release calendar: the ROIs by the month of their target date — Overdue first (red), then the months; 179 ROIs have no target date yet (not released, no date) filters the table to them.
  • Timeline (the default view; Table next to it): one bar per ROI across the months — Labeling (blue), Training (orange), Validating (purple); solid for what happened (from the first label, the first training job, the first model), hatched with a dashed outline for the plan (each stage's planned end), the release as a diamond (filled green = out, outlined = planned, red = the planned date passed), a red line at today. A released ROI with a new plan shows its next version: the planned stages after today and a second, outlined diamond. Released ROIs without a plan are hidden behind Show the n released ROIs without a plan. On a phone the bars scroll sideways and open at today. The models and releases imported on 2026-09-28 carry that registration date, so a stage can appear to start after the next one; the bar then shows the later one as under way. Estimated (USER 2026-10-18; faint, dotted): every ROI that is not released and not on hold is drawn to its release. A stage nobody dated gets an estimated end: where the previous stage ends + the median length of that stage among the released ROIs of the same modality (none → all released ROIs; none → 60 days); a stage under way past its usual length lets the next one start today; a stage skipped (a later one already started) is not estimated; without a planned release the release is estimated at the end of the chain (a dotted diamond). Only stages of 1 to 365 days count for the median: on the hub every released ROI came in with the 2026-09-28 registry import and its first label can be years older, which is history, not a stage (as of 2026-10-18 that gives CT labeling 242 days, MR 167, training and validating 60 — no released ROI has those dates). The tooltip says which median a segment used. A planned date always wins over an estimate. A release diamond that happened carries its package and the model version in it (wsch_1.3.0 · v1.0.2).
  • The table: ROI · Stage · Labels (labeled items holding the ROI against the goal, with a bar) · Projects · Best model by that ROI's own DSC (or, without a DSC for it, the latest model holding it; and the release it is in) · Target date (in 12 days / 3 days late) · Owner · Note; the release named with its package and model version (In release wsch_1.3.0 · v1.0.2). Filters (both views): All · GTV · CT · MR — GTV keeps the target volumes and combines with a modality: the registry category when it has one (target, target volume, GTV, CTV, PTV, ITV), else (the registry has no categories yet, 2026-10-18) a GTV / CTV / PTV / ITV / IGTV part in the name (GTV_Liver, CTVn_L2_L, CTV_Cervix^HR, LN_GTV, Prostate_CTV: 25 rows on the hub); and a search (ROI, owner, project); the ROIs that are moving come first, released ones last.
  • A row opens the ROI: its projects (labeled of items, goal), its best and latest model, its release, and the plan — stage (or automatic), when Labeling, Training and Validating should be done, the target release date, owner, labels needed, a note everyone sees (a later stage ending before an earlier one is flagged). A lead saves it; every change is logged and listed under Plan history (who, when, old → new), so a slipped date stays visible.
  • ROI requests (tab): anyone signed in uses Request an ROI — the ROI (a registry name or a new one), modality, priority, body region, needed-by date and why. Others add +1. A lead decides (Accepted, Planned, Done, Declined) with a note and the registry ROI it maps to; Planned or Accepted with a registry ROI creates its plan on the roadmap.

Hub routes (proposed §46): GET /ui/api/roi-board (rows per ROI × modality: projects with labeled_n — the project's own human labels whose ROI names hold it, alias-aware —, goal_n, model{best, latest} with the per-ROI DSC of the newest evaluation, released, plan, stage / stage_derived / stage_source, requests_open_n); GET /ui/api/roi-board/{roi}/{modality} (+ history); PUT …/plan (lead); GET/POST /ui/api/roi-requests, POST …/{id}/support, POST …/{id}/decision (lead). Live event roi_board.

What can go wrong

A model shows two versions, or the wrong oneThe same weights sit in several catalog folders (a duplicate_weights flag, e.g. Neck/1.0.1 = CrossRegional). The release names the catalog version with those exact weights, preferring the one that has metrics; trust the md5, not the folder name or git_tag.
Countries empty in the hubNo package of that release has been built for a country in ai-pipeline yet: empty means unknown, not "none".
Hub numbers differ from /specThey must not: both come from the same aggregation. A difference means the hub still holds an older registration (hidden list, train manifest or class mapping changed); run python3 scripts/hub_register.py reregister-all --apply in ai-pipeline.
Overwrite by mistakeThe replaced release is in /mnt/deploy/trash/release_<v>_replaced_<time>; move it back and create the package again (which re-registers it).
