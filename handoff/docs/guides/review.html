Reviewing labels

After this page a reviewer can work the review queue, give a verdict, ask for changes, and know how a verdict changes a label's state and what the labeler sees next.

Last verified 2026-09-30 · CONTRACT v1.6 · owner: labeling-server, labeling-web

What review is

Review is the lead's sign-off on a delivered label: one verdict per RTSTRUCT, the latest verdict counts. A verdict is approved or changes requested (a comment is required for the latter; per-ROI notes are optional). The verdict decides the label's state for training (label states): approved → approved, changes requested → changes_requested. A delivered label that nobody has reviewed yet is unreviewed — since D74 it may still be used for training if a lead or a policy includes that state.

The review queue (검수)

  1. Open 검수 (review). It lists assignments whose labels arrived (stage Labeled, stored delivered) and those a reviewer has opened (stage Review, stored in_review), oldest first, filterable by project and stage. Since v1.18 (D149) every web list shows the five display stages — see Stages.
  2. Each row (D153 W5: stage, project, patient, series as modality · description · date, assignee, delivered, ROI check, a 검수 button) compares the delivered ROI list with the project's ROI set (through the ROI registry's aliases): missing ROIs are flagged with their count (names on hover), extra ones counted. A red "AI pre-label" mark means the saved label still carries the pre-label structure-set name — ask for a re-save. Purpose and data level are on hover and in the drawer's revisions. Below 900 px the rows are cards. Since v1.19 (§26, D159) a 검사 column shows the hub's automatic label checks for the row (errors / warnings as icon + count, 미검사 while not checked yet); the drawer's 라벨 검사 section lists the findings — ROI, slice z, expected range — to look at before the verdict. They never block approval.
  3. Opening a row (or its 검수 button) starts the review (in_review) in the side drawer — beside the list on a wide screen —: what to do next, patient, series, delivered RTSTRUCT, revisions, earlier comments. Open the same series in OncoStudio to look at the contours.

Stages (v1.18, D149)

People see a row's stage, never the stored status: Unassigned (미할당) → Assigned (할당됨; stored assigned or in_progress, with a drawing note while someone holds the patient open) → Labeled (라벨 완료; delivered) → Review (검수; in_review, or changes_requested shown in red with the note changes requested) → Approved (승인); Excluded (제외) stands apart. The web reads the hub's stage / stages{} and applies the same rule itself when an older hub sends none, so the counts on the project page (stage chips, progress bar, project cards, public overview) add up to the stored ones: Assigned = assigned + in progress, Review = in review + changes requested. Status changes in the drawer history, the case page and the live feed read the same way ("Review (changes requested)", "Assigned (started)"). A lead's bulk Set stage on the board writes the stage's plain status (Labeled → delivered, Review → in_review).

A reviewer per item (v1.20 §27.6)

Each row can name its reviewer — a lead or admin. The labeler names one once the row is labeled (OncoStudio's case dialog, the web drawer: Reviewer…); a lead may set, change or clear it at any stage from labeled on. The named reviewer finds the row in To review on My works / 내 작업 and under the mine filter of the review queue (review/queue?mine=1). Any lead may still give the verdict — the reviewer is who is expected to. From D187 (v1.24, 2026-10-11) labelers review each other: the reviewer may be any labeler — since v1.30 (§43.1, U53) the row's own labeler too — as well as a lead, and the row's assigned reviewer gives the verdict (and may correct the label, §34) on both APIs; anyone else gets the row's reviewer or a lead. An admin can switch one account's review right off (web_user.can_review). Assigning items stays a lead's. A row already sent to the central PACS (stage Sent, after Approved) is final: its reviewer no longer changes.

On the web the 검수 page has a 내 리뷰 chip (?mine=1) and names the set reviewer under the labeler (→ name), both as the accounts' initials (LJM → SHK, v1.23 §31). The queue lists rows that carry a label revision; a row set to Labeled by hand without a file is in the reviewer's 내 작업 › 검수할 항목 but not in the queue. The drawer's 리뷰어 picker offers only people who can review.

Sending to the central PACS (web). A lead selects approved rows on the project page (or opens one) and picks 중앙 PACS 전송…. The confirmation lists the items and the destination (AE@host:port), names the selected rows that will not go (not approved, no label file on the hub, already sent), says that sending is final, and sends only after 위 항목과 보낼 곳을 확인했습니다 is ticked. The answer lists what was sent and what the hub refused with its reason. When the hub has no destination configured the button is disabled with that reason (and a 409 from the hub is shown in the dialog); nothing is sent. A sent row reads 중앙 전송 (Sent) in every stage chip, filter and pill; its drawer offers no verdict, only 다시 열기 with a required comment.

Send to the central PACS — final (v1.20 §27.7)

An approved label stays in the hub until a lead sends it: select approved rows on the project page (or open one in the drawer / case dialog) and press Send to central; the confirmation lists the items and the destination. The hub restores the patient's name, birth date and other identifiers from the image on the central share into a copy of the saved label (when the share holds no header for that image, the hub asks the central PACS itself for the patient record, since v1.59), sends that copy and throws it away — the copy the hub keeps stays de-identified. If neither the share nor the PACS can supply the patient record, or the record does not match the label's patient id, the row is refused (patient module unavailable) and nothing is sent; a failed transfer is shown with its reason and recorded. A sent row reads Sent, after Approved, and is final: it opens view-only, Request changes, reassigning and changing its reviewer are refused. If something must still be corrected a lead uses Reopen with a comment: the row goes back to the labeler as changes requested, the earlier send stays on record as superseded, and the corrected label is reviewed and sent again (the central PACS then keeps both, the newer one wins per ROI). The button is hidden for non-leads and disabled, with the reason, while the hub has no destination configured (production today).

Sent from OncoStudio before the review (v1.67 §27.9, hub S56): a row the app sent to the central PACS itself reads Sent · review pending and is not final — it is reviewed like a labeled row: Approve (one row or the bulk approve) keeps the send and makes it Sent, nothing is sent again; Request changes sets the send aside (superseded) and the row goes back to its labeler, whose corrected label is reviewed and sent again. Only an approved and sent row is final.

A sent file with a wrong Structure Set name (v1.50 §27.7 amendment, U133, D306 — 2026-10-29): a lead has the hub rewrite the naming fields of its stored copy (StructureSetLabel, StructureSetName, SeriesDescription := the project's RTSS name; UIDs, dates and contours untouched) and send the same object again; the row stays Sent with a new send on record and the earlier one superseded. The central PACS is expected to replace the object of the same SOP Instance UID — the hub checks with its own C-FIND and reports. This is the hub's relabel-resend management command, run on the user's order; there is no button, because since v1.50 §59.1a the name cannot be mistyped at save time.

Labels that were on the central PACS before the hub (v1.42 §27.8)

Some projects (first: Thoracic_LN) were contoured before the hub existed; their RTSTRUCTs already live on ONCOPACS, often under another structure-set name. For such items a lead runs central/reconcile (route or hub job) with the data list's labeler per item and the node stations the list notes as absent. The hub looks the item's image series up on the central PACS (a fresh query of the study on ONCOPACS, then each file itself — the hub's copy or a retrieval; read only), reads the ROI names of every RTSTRUCT that references the series, matches them to the project's target ROIs through the aliases, and for a file that covers every target (minus the listed absences) does three things at once: it becomes the item's label with the named person as labeler, the item is approved by the lead, and the row is recorded as Sent with origin: pacs — nothing is transferred, the file is already there. Files that cover fewer ROIs, items with no RTSTRUCT on central, and hub-made labels that never went to the PACS are listed with their reason and left as they are; the last group is sent the normal way. A dry run shows the lists before anything is written.

Giving a verdict

  1. In the drawer choose 승인 (approve) or 수정 요청 (request changes); write the comment the labeler will read (required for changes), optionally per ROI. The buttons are there for a lead whenever the stage is Labeled, Review or Approved — also on an approved row and on a data-list row that has no label revision (v1.18 §12, D150): a lead can send an approved row back with Request changes, or re-approve it. The row and the board refresh after the verdict; if the hub refuses (an older hub answers 409 for an approved row), its message is shown under the buttons and the buttons stay.
  2. Approve: the assignment becomes approved, the label enters the approved feed and counts for policies that include approved.
  3. Request changes: the assignment becomes changes_requested; the labeler sees the comment as a banner the next time they open the series in OncoStudio and acknowledges it. The rejected RTSTRUCT stays a labeled sample in state changes_requested; the corrected save is a new revision (unreviewed until you review it).

Bulk approve (v1.29 §42.3)

A lead or reviewer can approve many items at once from Training › Projects › <project> (the project's training view): Approve selected and Approve all labeled give the approve verdict to many rows at once (U52: the lead marks everything approved before training). Who: every account that may review — a lead or admin approves any row, a labeler whose account may review only the rows they are the reviewer of; others get 403. What it does: each row goes through the same approve as the drawer — one review row on the row's latest human revision, reviewer = you, origin=hub, status approved — so label states, the approved feed, policies and the app's next poll see ordinary verdicts. Approve all labeled takes every row of the project at stage Labeled or Review that has a human label of its own (the row's latest save in this project — v1.31 §44: a label of the same image in another project is that project's to review) — your own items included (v1.30 §43.1: no own-item rule). What it refuses (listed with the result, the rest still approved): not yours to review, no label, stage unassigned, stage assigned, stage excluded, sent (final, §27.7); rows already approved are skipped, not refused. For a lead or admin (v1.40 §60.3, U98, D261) only no label (no revision at all) and stage excluded remain: a row at any stage with a label of any kind — the labeler's own, an imported one, a legacy one — is approved; Approve all labeled reads Approve all with a label. Only approve exists in bulk — Request changes needs a comment per row. The live feed shows one line CODE · approved 38 items per batch; each row's own history keeps its line, marked bulk approve (origin bulk).

POST /ui/api/projects/{id}/review/bulk with {"verdict": "approved", "assignment_ids": [...]} (at most 500) or {"verdict": "approved", "all": true} → {ok, approved: [assignment_id…], refused: [{assignment_id, patient_id, reason}], skipped_n}; another verdict, both selectors or neither → 422. For a lead or admin (v1.40 §60.3) the approved revision is the row's latest delivery or correction, else its newest own revision of any kind (§44: human, external, Excel-era historical or merged, a pre-label last); a sent row counts in skipped_n; all: true is every row that is not excluded, not sent, not yet approved and has such a revision.

Review from OncoStudio

Since hub 1.6 (CONTRACT §12, D93) a lead can do the same from OncoStudio's Labeling › Review page: it shows the same queue rows as 검수 (GET /api/v1/review/queue is the web queue's query with the study / RTSTRUCT series UIDs and the round added), Open starts the review and Approve / Request changes… post the verdict through POST /api/v1/assignments/{id}/start-review and …/review. The hub records exactly the review row the web page would write — reviewer = the hub account the OncoStudio login is bound to, origin=hub — so the approved feed, label states, rounds and the labeler's My work do not know which door it came through. The login must be bound to an account with role lead or admin; a labeler or an unbound login is answered not available to your role (403), and a viewer without is_labeler may read the queue (masked IDs) but not sign off. Both pages stay: leads pick the browser or the tab.

Imported (legacy) reviews

Verdicts imported from the Excel workbook are recorded with origin=excel and legacy=true. They show on the assignment's history but do not count as hub reviews: they do not feed the approved set or policies, and a label whose only reviews are imported has state legacy.

Where they show (D95/H4): imported reviews and the workbook's comments sit under one collapsed block 이전 기록 (Excel) — closed by default — in the assignment drawer (every scope) and on the case page; hub reviews stay in the visible 검수 list and the project board no longer shows a comment count. Nothing is deleted and the importer is unchanged; the block simply keeps the old notes out of the main displays.
