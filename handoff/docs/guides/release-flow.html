How to use 배포: versions, the QA loop, a new release, downloads and the API

After this page you can read a package version, follow a bug from a JIRA ticket to the package that fixes it, make the next package from a folder on your PC with a diff you confirmed, mark it released after QA, and download any package in the browser or from a script. The hub's 배포 › 사용법 tab renders this very page.

Versions: what each number means

A package version is MAJOR.MINOR.PATCH or MAJOR.MINOR.PATCH.FIX (policy of the user, 2026-11-05; CONTRACT §77.1). Which number goes up is proposed by the tool from the difference between your folder and the base release; only the major decision is a person's.

ChangeNumberExampleWho decides
A new ROI appears (a new preset entry or a new class in a model's fingerprint)third (PATCH)1.7.2 → 1.7.3the tool (the diff shows + ROI)
A fix after a packaged release: model weights, a preset's routing or template, a channel rule, a landmark, an OD model — anything that is not a new ROIfourth (FIX)1.7.0 → 1.7.0.1 → 1.7.0.2the tool
A major change: architecture, a new pipeline, a changed output formatsecond (MINOR)1.7.3 → 1.8.0a person — tick 큰 변경 (major) in the wizard; any signed-in user may

Rules the tool enforces: the new version is numerically greater than the base; a FIX version shares the base's first three numbers; a version that exists as a folder or as a config tag is refused. You may edit the proposed version within these rules. Names with a prefix (wsch_1.3.0, smu_1.3.0) are customer builds outside the policy.

States. Every package has a state in its RELEASE.json: candidate (made, QA pending — 검증 중), released (QA passed — 배포됨), superseded (a newer one was released — 이전), withdrawn (철회). "Latest" means the latest released package everywhere — the dashboard, 모델 다운로드, the executor's default pipeline, the hub's model list (D333). Candidates are listed apart and are never defaulted; QA runs them on purpose. Packages made before 2026-11-05 (no RELEASE.json) count as released.

Model versions and the model release (v1.70 §84, U164, D344)

Two lines. A model (a trained network deployed to /mnt/deploy/models/<family>/<version>) is first a development version 0.y.z: the hub gives every deploy — the training wizard, a job's deploy stage, the loop's auto-deploy — 0.0.0 for a new family, else the family's highest 0.y.z plus one patch. Labelers train these models for the labeling loop; they are unstable and never production. A typed version at deploy time must be 0.y.z too (the hub answers development versions are 0.y.z).

Releasing a model. In 배포 › Model release a lead picks a deployed version (a 0.y.z folder, or a legacy folder deployed before this policy) and gives it a release version M.m.p with M ≥ 1 — proposed (M+1).0.0 over the family's highest released major, 1.0.0 for a family never released; editable to any greater M.m.p that is not a folder yet. ai-pipeline then makes the folder <family>/<M.m.p> as hard links of the source files and writes RELEASED.json (from which version, who, when, note); the hub records it (model_release) and from then on that model is the family's released model — in OncoStudio's picker, on the roadmap (Released, v1.0.0), in the ROI 카탈로그. An admin may withdraw a release (the folder stays; the model stops counting). Legacy folders without the file count as released only when a released package ships them, as before.

Packaging is optional. The workflow is deployed (0.0.5) → released (1.0.0) → packaged: a package (the release flow below) may ship the released folder; when it does, the roadmap names the package beside the version. Details: hub S60, ai-pipeline A16.

The QA loop, step by step

  1. Make a candidate with 배포 › 새 릴리즈 (below). It appears in 배포 › 릴리즈 as 검증 중 with its release notes and tickets.
  2. QA downloads it — 모델 다운로드 › 검증 중, or the API (below) — copies it into OncoStudio and tests. Problems become JIRA tickets in project OS (https://oncosoft.atlassian.net/browse/OS-…).
  3. Developers fix the model, preset or config, then make the next candidate from their folder. In the wizard's 릴리즈 노트 step they tick the tickets the package fixes (search by text or key; status and title come live from JIRA).
  4. QA passes → on the release page, any signed-in user presses 릴리즈로 표시 with the QA verdict, a note and the tickets; the state becomes released, the previous released package becomes superseded, and a comment Released in <version> with a link to the release page is posted on each ticket (untick Jira 에 코멘트 to skip). 철회 withdraws a package at any state.

The release notes (RELEASE_NOTES.md in the package folder, and the release page) are written by the tool from the diff and your summary, and list the tickets with title, status and link — so a reader can go from a package to the tickets it closed and back.

Making a new release from a folder

You need a folder on your PC that holds what changed — any subset is fine; everything you do not include is taken from the base release:

In your folderRecognised as
default_roi_presets.json, channel_modifications_config.json, Landmarks.json, MR_Landmarks.jsonconfig — compared entry by entry (ROI added / removed / renamed, routing, channel rules, landmarks)
<Family>/3d_final_model.pt + <Family>/global_fingerprint.jsona model (new family, or new weights of an existing one — the md5 and the class list are compared)
od_ct.torchscript, od_mr.torchscriptthe OD models
anything elseignored, listed as such
  1. 폴더 선택 — 배포 › 새 릴리즈, pick the folder (Chrome or Edge: the browser uploads the folder's files; the hub never reads a path on your PC). Choose the base release (default: the latest released). Upload runs per file with a progress bar; a file up to 2 GiB.
  2. 변경 사항 — read the diff: per config file the entries added, modified, removed; per model new / changed / unchanged; a summary line of ROIs and routings. Nothing is written yet.
  3. 버전 — the proposed version with the reason (+1 ROI → 1.7.1, fix only → 1.7.0.4). Tick 큰 변경 (major) for a MINOR bump. Edit the number if you must; the rules above apply.
  4. 릴리즈 노트 — write the summary (required); edit the generated change lines; tick the JIRA tickets (search) or paste keys / links.
  5. 확인 — one card with everything; 만들기. The tool creates /mnt/deploy/release/<version>/ (the base's models with yours replacing or adding, the six config files), writes RELEASE.json (state candidate) and RELEASE_NOTES.md, cuts the config git tag v<version>, registers the release in the hub, and shows the links. The base package is never modified — every change is a new folder (D331).

If a step fails, fix the cause and retry: the upload is kept for 24 hours. An abandoned upload expires by itself.

On the pages (labeling-web, W41): 배포 › 릴리즈 lists every package with its state badge (검증 중 · 배포됨 · 이전 · 철회) and 최신 on the latest released one; a version opens its page — the notes, the difference against its base (config entries, a models table), the tickets with live title and status, the zip and the country builds, and for anyone signed in the QA block (릴리즈로 표시 with the verdict, a note, more tickets and the Jira 에 코멘트 tick; 철회), both behind a confirm. 새 릴리즈 walks the five steps above in one page: the file list shows each path with its kind and a progress bar (two files at a time, a failed file retried alone), the version step proposes the number with the reason and keeps the field inside the rules as you type, the notes step searches Jira and takes pasted keys or links, and the done card links the release page, the zip and this page. 모델 다운로드 starts with the 최신 릴리즈 card (zip, KR · JP · US builds — a build not cached yet shows 빌드 중 · N초 and downloads by itself), then the packages grouped 배포됨 · 검증 중 · 이전 and the customer builds. 계정 › API 토큰 makes a token (shown once, with a copy button), lists name / created / last used and deletes one behind a confirm. 사용법 is this page, rendered in the hub (/deploy/howto#versions, #api, … link straight to a section). On 릴리즈 노트 the old bug-fix form is gone: a release card lists its fix packages with their state, each opening its release page.

What happens on create

Written by ai-pipeline (the one writer of /mnt/deploy/release; details on its component page). Before anything is written, the request is checked against the rules above. A refusal (bad_version, major_required, empty_summary, bad_jira_key, exists, empty_upload) comes back at once, and nothing is written. Then a background job, in this order:

  1. The new folder /mnt/deploy/release/<version>/. Every model family of the base: its weights are hardlinked (no extra disk; they are the same bytes), unless you uploaded that family's weights, which are copied in. Each family's global_fingerprint.json is the uploaded one or the base's, with version set to the new package version (as 새 패키지 always did). A family you uploaded that the base lacks is added. The six config files: yours where you uploaded them, the base's (hardlinked) otherwise. Nothing else of the base is carried over: its RELEASE_NOTES.md, RELEASE_REPORT.html and RELEASE.json belong to the base. The base folder is never written.
  2. RELEASE.json, state candidate: who, when, base, bump, major, the diff summary, your summary, lines and tickets (with the titles Jira gave at that moment).
  3. RELEASE_NOTES.md: # <version>, date, by, base; Summary (yours); Changes, the generated lines in a code block (+ ROI X (model Y), - ROI …, ~ ROI renamed: A → B, ~ routing: X MR_WholeBody → MR_AbdChest, ~ preset X: fields, ~ channel rule …, ~ landmarks …, * model Family 2.1.1 → 2.1.2 (md5 …) or fingerprint changed, same weights, * OD …), then your own lines; Jira (- OS-12 — title — (status) — link); QA, pending until the package is marked released.
  4. The config tag: the ai-pipeline repository's config/ gets the bundle's six files, in a commit of those files only, plus the annotated tag v<version>. Its message holds the summary, the change lines and Jira: OS-…, and its author is you. The tag is then pushed. Config 관리 lists it like any other version.
  5. The hub registration (POST /svc/v1/releases with state, base, bump, summary, tickets), sent by ai-pipeline's outbox; it retries by itself when the hub is away.

If a step after the folder was started fails, the partial folder is moved to /mnt/deploy/trash/release_<version>_failed_<time> (nothing is deleted) and the job answers the error; fix the cause and create again from the same upload. Marking released rewrites only state: the package's RELEASE.json (released, QA verdict), the QA section of the notes this tool wrote, and RELEASE.json of every older released package, which becomes superseded. A package made before 2026-11-05 gets its first RELEASE.json then; its hand-written notes are not touched. Withdrawing a released package gives the packages it superseded back their released state.

Downloading a package

  • In the browser: 배포 › 모델 다운로드 — the 최신 릴리즈 card at the top (the whole bundle as a zip, or a country build KR / JP / US with the permitted ROIs), then every package grouped 배포됨 · 검증 중 · 이전. A country build that is not cached yet is built first (a progress line, usually a few minutes for ≈ 2.5 GB) and the download starts by itself when it is ready. Zips need a login (D321); the lists do not.
  • One model: 모델 다운로드 › the family's row → the version's zip (release format, usage for a country).
  • From a script: the API below with a personal token.

The API (for QA scripts and automation)

Make a token once in 계정 › API 토큰 (any signed-in user; the token is shown once — copy it; revoke it there when it leaks). Send it as Authorization: Bearer olt_…. The token works only on /api/v1/releases…; every call is logged with your name. Base URL: http://10.101.1.183:8790.

CallAnswer
GET /api/v1/releases{releases:[{version, state, base_version, bump, created_at, released_at, size_bytes, notes_summary, jira_keys[], download_path, country_download_paths}], latest_released, latest_candidate}
GET /api/v1/releases/{version}the package: RELEASE.json fields, release_notes_md, jira[] with live title and status
GET /api/v1/releases/latest?channel=released|candidatethe newest package of that channel (404 when none)
GET /api/v1/releases/{version}.zipthe whole bundle, streamed
GET /api/v1/releases/{version}/country/{KR|JP|US}.zip200 the country build when cached; 202 {job_id, retry_after} while it is being built — call again after retry_after seconds
GET /api/v1/releases/latest.zip?channel=released&country=KR307 to the concrete version's path (follow redirects)
TOKEN=olt_…   # from 계정 › API 토큰
H="Authorization: Bearer $TOKEN"
B=http://10.101.1.183:8790/api/v1

curl -s -H "$H" $B/releases | jq '.latest_released, [.releases[] | {version, state}]'
V=$(curl -s -H "$H" "$B/releases/latest?channel=released" | jq -r .version)
curl -L -H "$H" -o "$V.zip" "$B/releases/$V.zip"

# a country build: poll until 200
until curl -s -L -H "$H" -o "$V-KR.zip" -w '%{http_code}' "$B/releases/$V/country/KR.zip" | grep -q 200; do sleep 30; done

A bad or revoked token answers 401 {detail:"bad_token"}. The same calls work in the browser under /ui/api/deploy/releases… with your session (what the pages use).

How the hub treats a token (labeling-server, S52): the token is olt_ + 40 characters and is shown only in the reply that makes it — the hub keeps its SHA-256, so a lost token cannot be shown again: revoke it and make a new one. You may hold at most 10 live tokens (the eleventh answers 409 too_many_tokens); an admin can list and revoke anyone's under 관리. A call acts as you, with your current role: a deactivated account's tokens stop working at once. Only channel and country are passed on from the query; a 307 points at the hub's own /api/v1/releases/… path (so curl -L keeps your token on the same host), a 202 is passed on unchanged. Each call — a refused one too — is one line in the hub's audit log (your name, the path, the status, the token's number); the token's last used time is shown in 계정 › API 토큰. The token opens nothing else: every other /api/v1 route and the web ignore it.

What can go wrong

"version must be greater than the base" / "shares the base's x.y.z"you edited the version against the rules above → take the proposal or fix the number.
"exists"a folder or a config tag already has that version → the proposal skips it; choose the next.
"major_required"a MINOR bump without the 큰 변경 tick → tick it (a person decides major).
"qa_required"릴리즈로 표시 without a QA verdict → choose pass (or fail, which leaves the state).
Jira unavailablethe release page shows ticket keys as plain links and the wizard's search is empty → the Jira settings on the platform host are missing or refused (401); ask the platform owner. Nothing else is blocked.
The folder picker is greyedyour browser has no directory upload (Safari, Firefox without the flag) → use Chrome or Edge, or pick the files one by one.
A country zip answers 202 for longthe build is running (≈ 2.5 GB); keep polling as in the example. A 5xx means the build failed — the release page shows the job.
The dashboard still says LATEST 1.7.0 although 1.7.0.3 existsthat is the rule: 1.7.0.3 is a candidate until QA marks it released.
