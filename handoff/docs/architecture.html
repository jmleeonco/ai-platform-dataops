The picture

Agents: who orders whom (U10, 2026-10-08)

The user talks to one agent, the orchestrator. It turns a goal into work orders, sends them to the role agents, collects their reports, checks the result and keeps this page current. Each role agent works in one ORCA workspace (a directory) and owns the code listed below; the user may also give oncostudio, ai-pipeline or ai-platform-dataops an order directly, and those agents tell the orchestrator. Names and paths: onco-mlops/WORKSPACES.md; the protocol: onco-mlops/COLLABORATION.md.

Rules that keep the integration sound

  • One owner per integration point: a contract section is implemented by one role on each side and proven by its tests plus a mock the other side can run.
  • Additive only across the boundary: new fields, tolerant parsers, feature flags; old clients keep working; migrations never drop or rename.
  • The pipeline is pinned: verify must pass before the pin moves; research code is requested, not edited.
  • Production is shared: /mnt/deploy, the GPU (flock), host memory (≥ 12 GB free before heavy work), production windows.
  • Source control (U121, D284/D285): one private GitHub repository per system under oncosoft-io; a role pushes only its registered branch to that origin, after every commit it reports; pull requests are the path for contributors without host access (COLLABORATION.md §11); no force push or history rewrite unless a person asks.
  • Adding a component means a registry row, a CLAUDE.md from the template, a STATUS file, a contract section with a mock, a health URL — and a docs page here.
