Label states (v1.4)

Every label revision has exactly one state at a point in time as_of. Training cohorts may include any of them; the state travels with the split so a model's training data can always be characterised afterwards.

StateDefinitionTypical origin
approveda human revision whose latest hub review as of as_of is approvedreviewed in the hub's 검수 page
changes_requesteda human revision whose latest hub review has any other verdictthe labeler has been asked to fix something; the RTSS still exists and is a valid label
unrevieweda human revision with no hub review as of as_ofsaved from OncoStudio, not yet reviewed
prelabelkind=prelabel: an AI pre-label not yet replaced by a human deliverableproduced by a training job's predict stage and pushed to the project's destination
legacykind=historical, or a revision whose only reviews were imported (origin=excel)the frozen labeling workbook, old RTSS files
Selection rule"Latest revision per image series among the requested states": revisions whose state is in the request, ordered by labeled_at (sent time, else creation) descending, ties human > historical > prelabel. So states=approved yields the latest approved revision even when a newer unreviewed one exists (exactly the pre-v1.4 approved set), and "all states" yields the newest label of any kind.
Prefer, never refuseA training policy lists the states it includes (existing policies keep approved only, so nothing changed for them; new ones default to all states). The wizard starts with all states selected, approved first. No hub or executor path refuses a job because of a label state (D74).

Split provenance

A registered split (dataset_version) is identified by model_family and split_hash. The hash is computed the same way by the executor, ai-pipeline and the hub's deploy sync (golden vector in all three test suites):

line   = role \t sample_id \t image_series_uid \t rtss_series_uid \t image_sha256   (one per item, sorted)
split_hash = sha256("\n".join(lines))
sample_id  = the pipeline's sample id, else "img:" + sha256(normalised image path)[:20]   (never a file stem)
image_sha256 = SHA-256 of each decompressed input file

The label state is provenance about the RTSS the hash already names (a different revision is a different RTSS series UID), so it is stored per item (split_item.label_state, label_kind) and as a histogram on the version (dataset_version.label_states, plus the cohort request: as_of, states, policy), without changing the hash (D75). Splits registered before v1.4 show unknown.

The pre-label loop

  1. A policy (or a person) starts a job; its predict stage produces RTSTRUCTs marked AI_PRELABEL (ROI names end in _pre).
  2. The executor posts them to the hub (POST /svc/v1/prelabel); the hub stores a label_revision(kind=prelabel), flags the assignment, and C-STOREs to the project's configured destination (dev: the Windows OncoPACS; production: none unless a lead enables it).
  3. OncoStudio shows the suggestion; the labeler opens it, corrects, saves — the human deliverable supersedes the pre-label and the hub measures the correction.
  4. The corrected revision is unreviewed until reviewed; it can already enter a training cohort if the policy or wizard includes that state.
