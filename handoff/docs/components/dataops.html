Component · ai-platform-dataops

The data management DB and the dataset intake flow

After this page you can say what the data management DB holds and where each row came from, take a dataset folder from analysis to Central with the owner's approval, find any dataset, series or ROI in the catalogue, and run, test, back up and restore the system.

Last verified 2026-11-09 · CONTRACT v1.63 §78 · owner: ai-platform-dataops

What it is for

A system on the platform host (10.101.1.183, repo /drive/project/ai-platform-dataops, branch main) with two jobs:

  • Intake. It takes a medical imaging dataset folder and brings it to the central PACS in a controlled way. An agent and deterministic code analyse the folder. A 2-subject sample goes to a local OncoStudio for a visual check. Then the owner approves, and the full set goes to Central and is registered in the DB.
  • Catalogue. The same DB is the company-wide catalogue of datasets already in use. It holds a read-only copy of the LAB DB and of the model-training bundles in /mnt/deploy/data, so one place answers which dataset holds which patient, series, split and ROI.

A series can belong to datasets of more than one origin. dataset_series holds the memberships, so the same image is stored once and listed under each dataset that uses it.

ROI names

Each RTSTRUCT series stores its ROI names (series.roi_names, a JSON list) and the image series it points at (series.referenced_series_uid). That links a ROI name to the CT/MR it was drawn on. On 2026-11-09 there were 18,661 RTSTRUCT series:

  • 18,296 have ROI names.
  • 17,934 are linked to an image.
  • There are 4,046 distinct names.

Names are stored as written in each file. Spellings are not mapped to one organ.

The intake flow

Everything happens in the web, one page per run at /runs/<run_id>. A run's files live in runtime/runs/<run_id>/. Statuses:

ANALYZING → PLANNED / NEEDS_INPUT → PILOT_READY → PILOT_SENT → APPROVED → PREPARED → CENTRAL_SENT | CENTRAL_PARTIAL | CENTRAL_FAILED

Deterministic code (spec.py, plan.py) checks every field. One dataset at a timeExtracting samples, the pilot and the Central send all freeze image files on this host. They refuse to start while another run still holds image files, and the message names that run, its status and its size. The run page shows that run with an 이 서버의 영상 삭제 (delete images on this server) button for the owner. The system never frees the slot by itself for a run that is not final.
Internal dataFolders listed in DATAOPS_INTERNAL_ROOTS go out pseudonymised (profile pseudonym-v2: names, institution, IDs and order numbers removed, UIDs replaced, dates kept). Public data is never pseudonymised. The run page shows the source values next to the outgoing ones.

Re-running the imports is idempotent and cheap, because the bundle header scans are cached in runtime/deploy_scan/:

python -m dataops import-legacy [--dry-run]
python -m dataops import-deploy [--dry-run] [--rescan]

Both read only: oncolabdb through a READ ONLY session, /mnt/deploy/data as files, and Central by C-FIND and C-GET of RTSTRUCT (approved 2026-11-03).

Hard rules

These are the owner's rules (the system's docs/HANDOVER.md §2 and AGENTS.md). They are part of §78 by reference, and no work order relaxes them.

RuleDetail
Central is productionOnly runs the owner approved in the web and asked to send go to Central. Nobody approves or publishes on the owner's behalf. Central has been enabled since 2026-11-02.
Local sender guardlocal_send.py / /send-local-scp refuse any host but this machine and the review PC, and refuse AE ONCOPACS. Central goes through publish.py only.
The existing MariaDB (10.101.1.4)SELECT only. No export into oncolabdb (owner 2026-10-29). Only the LAB dataset tables and the encryption maps are copied; reading any other table's rows needs the owner first.
/mnt/deployRead only. On /mnt, only the nightly backup writes.
IdentifiersPatient names, IDs and dates from internal data never appear in chat, commits, STATUS or reports. The web shows real source values on the source side (owner 2026-10-30/31); only the outgoing side is pseudonymised.
SecretsOnly in ~/.config/ai-platform-dataops/env (mode 600), never in git, docs, backups or chat.
NamingThe PatientID prefix follows the company rule in Notion ("04-1 Data prefix 규칙"); the code is a copy.
ReportsEvery dataset gets the same numbered tables, with no free-form write-up.
Images are transient (§78.6)The user, 2026-11-09: "the db agent should not store image permanently. The images should be in central scp. Storing image locally in 183 forever would cause memory issues. It may store one project's image (if necessary) at a time." Image files on this host are working copies of at most one dataset. The lasting copy is Central for a published run, and the source folder for any other run. After a purge, the record stays: run.json, the plan, the sha256 manifests, the transfer journals, the report and the sample headers. A purged run can be frozen again from source + plan, and the manifest proves the bytes are the same. The reviewer's pilot copies in the PC's OncoPACS are not touched.
No transfer without the user (U156)Nothing is sent to Central or to the local SCP, and no pilot or approval happens, unless the user says so explicitly. Purging and the slot check send nothing.

The platform's limits apply too: no sudo, never stop a process you did not start, the memory gate before the full suite, and pushes go only to main on origin (COLLABORATION §5).

PurgeRun page → 이 서버의 영상 삭제 (delete images on this server): type your name and confirm the dialog. Or python -m dataops purge <run>, which asks first; --yes skips the question. It deletes the run's artifacts/ folder and any *.dcm / *.nii / *.nii.gz, keeps the record, and does nothing on a second call. Purge is refused for an approved run whose Central send is not finished, because its frozen bytes are what was approved. Automatic purges: after a complete publish + registration, after a failed analysis, and when a new analysis of the same folder replaces an older pilot-stage run.
BackupUser crontab 00:30 → ops/backup/nightly_backup.sh → /mnt/ai-pipeline/backups/ai-platform-dataops/<date>/: dumps of both schemas, run metadata, a repo bundle and manifest.json, with retention as §65. Plus …/ai-platform-dataops-files/, an rsync snapshot of runtime/runs without images: PIXEL_EXCLUDES leaves out artifacts/, *.dcm, *.nii and *.nii.gz, and the tar of run metadata does the same. Image bytes from earlier snapshots were removed once on 2026-11-09 with backup_tool.py prune-pixels. Errors go to /tmp/ai-platform-dataops-backup.err.
Restore checkops/backup/restore_check.sh [YYYY-MM-DD] restores into a throw-away MariaDB container and compares the row counts of both schemas with the backup's. It also checks that the repo bundle holds the recorded commit and unpacks the run metadata. Finally it checks the run snapshot: every manifest still matches its sha256, and no image file is present. It touches nothing live.
NFSThe /mnt2 mount sometimes returns "not found" for minutes. Every input read goes through dataops/nfs.py, which falls back to the read-only mirror.

Open threads

  • No login on the web. It is bound to the LAN; a login, or a hub login in front of it, is not decided (§78.4).
  • The LAB DB account is a shared admin account. A SELECT-only account and a password rotation were recommended to the owner; neither is done yet.
  • No read-back check on Central. Sends are journalled per instance, but what Central stored is not read back.
  • The licence tier of the one published public set (PUB vs NC) is still open with the owner.
  • Internal sets with identifiers in folder names and tags are not ingested until a de-identification profile and an owner decision exist. Duplicate pilot runs of one internal set are waiting for a clean-up decision.
  • Naming-rule questions are open with the owner.
  • Speed. The dashboard takes about 1.3 s; the per-patient view of /browse takes about 1–2 s.
  • No consumer yet. The hub's 데이터셋 (datasets) pages and the executor do not read this catalogue. The first one is a §78 amendment.
