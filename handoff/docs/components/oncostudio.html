What it is for

The labeling build is the same OncoStudio the clinics use, plus a recording layer: every contour session, stroke, tool change, edit command and save is recorded locally and uploaded to the hub, RTSTRUCT saves carry their provenance (which assignment, which project, which pre-label they started from), patients can be claimed so two labelers do not draw the same series, and the labeler sees their assignments, the project's ROI checklist and review comments inside the app. The regular product is unaffected: the whole layer sits behind one façade with a real and a stub implementation, switched at configure time.

The build switch

The environment variable LABELING_MODE=1 at CMake configure time is the only switch. It selects the real façade (OncoStudio.Controller.Labeling.cpp, OncoStudio.View.Labeling.cpp and the labeling-owned files) instead of the stubs, links Infrastructure.Service.Activity, and defines ONCO_LABELING_MODE for labeling-owned files only. Shared files contain no #if: they call façade functions that are no-ops in the regular build. Flipping the switch on an existing build tree costs a full rebuild.

How work reaches the hub

  1. Record. The recorder receives events from the extension points (session opened/closed, tool requested, stroke, edit command, save) and appends them to a local spool file per session. Recording never blocks drawing (a perf gate proves the budget) and a kill switch stops it if the hub is unreachable for too long.
  2. AI provenance (v1.47 §62.1, U128-1, D291 — O24). Every AI result has an id and says what it wrote, every later edit says which ROI it touched and from which AI result that ROI came, so the hub can tell accepted as-is from edited. ai_run / autoseg_run keep every field they had (the Records feed shows model as a string) and add run_id (uuid), tool (auto_contour = the viewer's Auto Segmentation · interactive_seg · gtv · prelabel = a viewer opened with an AI_PRELABEL), model_ref {family, version, md5} where a registry model is known (a pre-label's RIBS 1.0.3), rois: [{name, roi_number, voxels}] and, for Interactive Seg / GTV, prompts (one run per result). stroke_commit, edit_command, roi_rename (roi = the old name, name = the new one), roi_remove, undo, redo carry roi and origin_run_id ("" = hand-drawn). The AI's own write of its result (the edit command named nnInteractive / GTV Interactive) is marked ai_write: true and gives the run's voxels (voxels_after); it is not a user edit. Undo prompt is an undo with run_id (the run taken back); Ctrl+Z of an AI result is an undo with that run_id. Either way the ROI's origin goes back to what it was before that run (an auto-contour, a pre-label or an earlier Interactive Seg result, with its edits; none = hand-drawn), named in the undo's origin_run_id. A mask edit that changed no voxel (a brush stroke that erased nothing) does not count as an edit. The save's deliverable lists per ROI origin_run_id, edits_since_run (mask edits and renames after the run), voxels_at_run and voxels_saved (inside = value ≥ 128, the same count at run and at save). The bookkeeping runs on the recorder's thread (RoiEffortTracker::annotate; the masks are counted there, never on the UI thread); the hooks are ActivityHooks::aiRun / autosegRun / aiPromptUndone / structureSetLoaded, wired in LabelingWiring. An older hub ignores the fields. Test: ActivityRecorderTest provenance.
  3. Notes on every item (v1.47 §64, U128-3, D294 — O25). ClaimClient::fetchItemNotes / postItemNote / editItemNote (PATCH) / deleteItemNote (DELETE) on /api/v1/projects/{code}/items/{item_id}/notes (item_id = the assignment id, else the image series UID), parsed by WorkspaceParse::itemNotes / itemNoteSaved (HubItemNote: id, author_alias, at, edited_at, text, origin, mine, can_edit, can_delete; routeMissing = the framework's own 404/405, not item not found); HubNoteLatest on the project rows (+ notesCount) and the My works rows. The gate is the row's note_latest key (the contract version stays 1.45 until S32): with it, ProjectPage::addNote posts to the item's list (a routeMissing answer falls back to the §17 comment), CaseSections::setItemNotes puts the list in the History timeline (author, time, (edited …)) with Edit note… / Delete note… on a note's context menu where the hub says can_edit / can_delete, the Stage & review card has Latest note, My works a Note column on both lists; without it everything stays as before. Ports fetchItemNotes / saveItemNote / askNoteText (OncoStudioSmokeHarness leaves them empty). Test: headless LA-114.
  4. Model type on the Train strip (v1.47 §63, U128-2, D292 — O26, read side; the control is removed by v1.57 §74.1 (U144), see below). WorkspaceParse::projectLoop keeps policy.model_type / policy.model_name (HubProjectLoop::policyModelType / policyModelName) and model.model_type; loopStripView shows the family as the hub names it (Model RIBS_2d 1.0.4) and what the next Train makes (· next: RIBS_3d (3D); nothing on a hub without the policy name). The Models page and the Auto-contour picker take family names verbatim (no name is parsed), so <CODE>_3d / <CODE>_2d show as they come. 3D | 2D beside Train (S33, D295 — option A of the O26 question): a lead or an admin of the project picks the model type; the app sends PUT /api/v1/projects/{code}/round-policy {user_id, model_type} (ClaimClient::setRoundPolicyModelType → ProjectWorkspace::setModelType), the reply {model_type, model_name, version, next_version} goes into the strip at once (· next: RIBS_2d 1.0.4 (2D)) and /loop is asked again (an answer asked before the change does not undo it for 10 s). Anyone else sees the choice disabled with Only a lead or an admin of the project sets the model type.; a refusal (403, 409 the template has no train.mode) shows the hub's reason and the choice goes back; a hub without the route says to use the web page. Setting the type is not a training call: Train still opens the project on the Labeling Tracker web page (D141). Tests: headless LA-115, LA-116.
  5. Upload. The uploader batches spool entries to POST /api/v1/batches (no token since D62), retries with back-off, and only deletes a spool segment after the hub acknowledged it. Edit commands are sent before the strokes they contain so the hub can replay them in order.
  6. Save. When an RTSTRUCT is saved as DICOM, the save dialog's project section adds assignment_id, the project's RTSS name convention, purpose and data level, and — when the session started from a pre-label — the pre-label's revision UID, so the hub can measure the correction; for an assignment of a labeling round the detail also carries round_id (v1.5; omitted outside rounds). The hub turns the save into a deliverable and a label_revision of state unreviewed.
  7. Label file at save (v1.20 §27.1, D163). The save path (labeling-only SaveTransfer.LabelingProvenance.cpp) stamps StructureSetDescription = oncolab project=<code> assignment=<id> (the project from a thread-safe assignment → project map that My works, the project rows and for-series fill), keeps the written file's bytes, and, when the save is stored (file / OncoPACS-internal / C-STORE callback), hands them to a pool thread together with the save’s deliverable event (held, see the next item): deidentifyForTransport (DCMTK; the §11.5 pre-label restore's tags removed, PatientID / sex / character set / UIDs kept) → ActivityRecorder::enqueueLabelUpload (a queue push; the worker writes <spool>/labels/pending/<sop>.json with the full body). The uploader thread posts each file to POST /api/v1/labels with its own back-off (15 s … 10 min, 8 tries → labels/failed, retried at the next start; a 4xx other than 401/408/429 → labels/rejected); a final failure is said once as a toast on the main window (installLabelUploadNotes). Measured on dev: the caller's cost 0.01 ms; 200 stored:true, the repeat stored:false, label_file on the row, checks in 3 s (ActivityRecorderTest workflow). A sent item opened view-only (setItemViewOnly) is saved outside the project (no assignment, no upload). In-app acceptance 2026-10-10: the stamp is written whole (StructureSetDescription is ST, up to 1024 characters — it was cut at 64, which truncated the assignment id), and the save dialog names the file after the project’s rtss_name from the item’s assignment even before the per-series project lookup has answered (a fresh item kept RT Structure Set).
  8. Deliverable after the store (v1.38 §53.2, U85, D247). The hub registers a label revision from a sent deliverable event (on_deliverable), so that event goes only once the hub has the file. Before, the save recorded it at once and queued the upload behind it; when the upload never landed (the hub refused it with 403 not the assignee, the reviewer or a lead, the file could not be read back or de-identified, the retries ran out), the hub kept a revision whose file existed nowhere — Chest_2023_0010 (10-11, saver not the row’s assignee) and QIN-BREAST-01-0011 (10-19) failed Thoracic_LN job 63. Now deliver() in SaveTransfer.LabelingProvenance.cpp asks deliverablePlan(status, uploadsLabel) (LabelingWorkflow): a project save (an assignment’s) passes the event as a HeldDeliverable to ActivityRecorder::enqueueLabelUpload, which writes it to <spool>/labels/held/<sop>.json before the job; the uploader’s outcome settles it (settleHeld): stored (200) → the event with the save’s status and sent_at; refused (4xx) → failed with label not stored on the hub: 403 …; retries ran out → failed now, still held (the job is retried at the next start and a later success records it). Stored while no session of the saver is open → labels/held/ready/, recorded at that user’s next login (never in another user’s session). A label that cannot be queued at all → labelNotQueued: failed at once and the note. A save without an upload (no assignment: the §34 upload gate said no, or no project) is recorded as saved_local, never sent — the hub keeps the row and registers no revision. The main-window note (labelUploadFailedNote) says The project does not have this label for a refused / unqueued file, … not yet; the upload is tried again at the next start when the hub was not reachable. The hub already creates the revision from the upload when it comes first (label_files.store), and on_deliverable then moves the row. Tests: ActivityRecorderTest held (in-process mock hub: no deliverable while the hub has not answered, sent after 200, failed after 403, held across another user’s session, failed when not queued), headless LA-99.
  9. Claims. Opening a series claims the item for the labeler (/api/v1/claims, v1.20 §27.0: the body carries image_series_uid, the release names the series; closing a series' last tab releases that item only). Someone on another study of the same patient is no conflict (also filtered app-side for an older hub); a sent item opened view-only makes no claim.
No patient namesPayloads carry PatientID, study and series UIDs, never names; the hub rejects any payload with a name field (422).

The Labeling tab (D92, D98)

The labeling build adds one Labeling tab to the main-window tab bar (next to Auto-Segmentation and Settings; Ctrl+Tab cycles through it). Since 2026-10-01 it is project-centric (D98): the team works in projects, so the tab opens on the projects list and everything else hangs off the project the labeler opened. Training stays in the hub's web UI. The regular product has no such tab: the tab is created by the façade (Labeling::installWorkspaceTab, stub = nothing) through a shared, inert extension point (MainWindowTabsWidget::addExtensionTab).
