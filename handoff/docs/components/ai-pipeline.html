ai-pipeline: regulatory metrics, packaging and the ROI registry

After this page you can say what ai-pipeline computes and packages, how its GPU queue and leak guard work, what it registers in the hub, and how it is run in dev and production.

What it is for

ai-pipeline (모델 배포 파이프라인) is the release pipeline's metrics and packaging app. It measures every deployed model version on its data versions (DSC and HD95 per ROI, the regulatory 성능 표), builds the release packages that ship to clinics, owns the ROI registry file (official ROI names and their aliases), and tells the hub what it found: evaluations with per-case rows, releases with their countries, split demographics, bundle-validation results and model flags. The hub stores those figures and shows them; it never recomputes them. Leads open ai-pipeline pages inside the hub (embedded, signed in by the hub), or directly at http://10.101.1.183:5000 on the LAN.

/spec: regulatory metrics

An evaluation is one model version scored on one data version's validation cases: inference/calculate.py runs the model on every case and writes one JSON per case under /mnt/deploy/metrics/<model>/<model version>/<data version>/VALID/. Every page and every hub registration aggregates those files the same way (app/spec/metrics_reader.py): per-ROI mean/median DSC and HD95 and n, after dropping hidden model versions and leaked cases. A pair that already has results is shown, never recomputed.

  1. Queue. 추론 관리 (/spec/manage) lists pairs that need numbers; 실행 enqueues them. Jobs live in a durable SQLite queue (instance/inference_queue.sqlite): they run detached from the web server, survive a restart (the worker re-adopts a running job by pid, start time and job tag) and run one at a time.
  2. Admission. Before a job starts the worker waits until the host has ≥ 12 GB free memory (D51) and takes the shared GPU lock ~/.cache/onco-gpu/admission.lock (§7.7, also used by the executor's GPU stages). The lock is held by the job's process for exactly as long as it runs. Training is never pre-empted; evaluation waits.
  3. Automatic jobs. The hub's change feed (GET /svc/v1/changes, D36) wakes the worker when a model or data version appears; it queues the new model on its family's latest data (or the new data with the latest model), origin auto, capped at 8 GPU-hours per KST day. Manual jobs are never capped.
  4. Leak guard. A case the model version trained on is never scored. The training split comes from the hub (looked up by the md5 of the weights, GET /svc/v1/models/{md5}/training-split), else a train manifest, else the newest data version not newer than the model (marked 추정). Evidence is a shared DICOM series UID or byte-identical image content (SHA-256), never a patient ID or name. Leaked cases are skipped, dropped from every aggregate and listed on the pair's detail page. A pair whose every case leaked cannot be queued.
  5. Profiles. The 인허가 프로파일 pages cross-tabulate train and valid demographics (sex, age, vendor, slice thickness, contrast, country) from the per-case JSONs, per package, per model × data version, or over every deployed model (/spec/profile/all, each non-hidden model at its newest evaluated version; models never evaluated are listed as 미평가). Since 2026-10-14 (RA request) a profile has: a 모델 정보 table (evaluated and newest model version, data version, newest release that ships it, train/test N, ROI and permit-ROI counts, failures); CT and MR apart (Data Summary per modality, the MR one without the contrast block; ROI Test CT and ROI Test MR tabs); ROI rows grouped into H&N / Thorax / Abdomen / Pelvis / Whole Body / Others (the ROI board's region classifier; brain counts as H&N); one row per modality × ROI × model, counted by the same rules as every other /spec number (per-patient relevant classes, empty-GT cases out, leaked cases out), with a class nobody annotated still listed as N = 0. A package lists each ROI once, from the model its release presets name (CT default_model, MRI template); the all-models profile lists every model's rows and stars the newest release's default. Each row shows the countries whose permit list (Permit 동기화) names the ROI. Criterion by mean GT volume (GT voxels × voxel size from the metric itself — the result's volume field misnamed or zeroed channels and is only a fallback) — Small < 10 cc: DSC ≥ 0.5 (RA's sheet); Medium 10–150 cc: DSC ≥ 0.65; Large ≥ 150 cc: DSC ≥ 0.8 — DSC only (DSC 판정); 95%HD is reported, never judged, as in RA's sheets. The 기준 미달 tab gives each failing row its spread (median, minimum, share of cases meeting the limit, mean without Tukey outliers, DSC = 0 count), the worst cases, other evaluations of the same ROI and modality that meet the DSC limit (N ≥ 3), and a 조치 record (status 미조치 / 조치 중 / 조치 완료 / 사유 기재 + note, by any logged-in user, with history; data/profile_actions.json, key <modality>|<ROI>|<model>, so it follows the pair into every view). Only standard evaluations (a model version on its own family's data) are registered in the hub; cross-model and custom-input runs (OS_INPUT_DIR) stay local (CONTRACT §3, kind='standard').

What a per-case result holds (…/VALID|TRAIN/<case>.json): the case's split row, per-ROI DSC/HD95 (valid only), and from one DICOM header per case sex, age, vendor, slice thickness and, since v1.5, scanner model, modality, study date, spacing between slices, pixel spacing and institution (only when the header has them), plus dicom_source (local or central:<how matched>), population and contrast. A header of a non-image object (an RTSTRUCT in a folder that holds nothing else) gives only patient and study fields: its equipment fields name the software that wrote it, so the calculator looks up the image's own header on the central SCP instead. Results written before that rule were corrected by inference/fix_scanner_vendor.py (2026-10-14, 681 results: the image header on the central SCP, else the scanner model name from the headers or the case metadata registry, else unknown; audit log and --revert). MR results also carry mr_weighting (T1/T2 from SeriesDescription, else TR/TE), mr_contrast (ContrastBolusAgent or a contrast keyword) and field_strength (1.5T / 3.0T) for the workbook's 영상종류 rows; older results get them from backfill_dicom_meta.py --mr-series (header reads only, 20:00–07:00 KST, marked mr_series_source). Readers treat every key as optional, so results written before a key existed keep working. Results older than v1.5 got the new keys from a header-only backfill (inference/backfill_dicom_meta.py --facets: no inference, 20:00–07:00 KST and ≥ 12 GB free before each model family; being CPU/IO-only it never takes the GPU admission lock (D87), so it never delays a training or evaluation stage; it marks each case facets_source).

Case metadata registry. Many deployed cases have no readable DICOM header (NIfTI-only public datasets, internal data not on the central PACS). Their sex, age, vendor, slice thickness and population come from /mnt/deploy/config/case_meta/<group>.json: one file per source group, matched by dataset name, patient-ID or image pattern, every value stored with its source (dicom: original header, clinical: clinical table, dataset: documented group-wide fact, nifti: original spacing; no image-based estimates are adopted). Internal groups are keyed on the patient ID, never on names. inference/case_meta.py fills null fields only (header values and population rules win) and records meta_sources in the result: the calculator does it while scoring (OS_CASE_META=0 turns it off) and inference/backfill_case_meta.py does it for existing results (JSON only, no GPU; --revert undoes exactly what it filled). The 인허가 프로파일 (page and xlsx) shows a 값 출처 table that counts each category's values by origin (header/rules vs registry source kinds), and the 사용된 데이터 list shows demographics for every row of the split (train rows too; never-evaluated rows straight from the registry) with each value's source as a tooltip. The registry location is CASE_META_DIR (env OS_CASE_META_DIR); the hub reads the same files to fill its project rows (D138a).

The ROI registry

/mnt/deploy/config/roi_names.csv is the platform's list of official ROI names and their aliases, exactly two columns: roi_name,alternative_names. ai-pipeline is its only writer: the ROI 관리 page edits it (data team, research) and writes it atomically, aliases joined with | (a , list inside one quoted field is also read). The hub mirrors the file and is the single read endpoint for everyone else (/svc/v1/roi/registry.json|csv, with X-Registry-SHA256 headers, §3 and §6.5); a consumer that falls back to the file while the hub is down records the source and hash in its run. There is no model column; which model delivers an ROI comes from the model fingerprints.

What it registers in the hub

Every registration goes through a local outbox (instance/hub.sqlite): an intent is queued, a worker builds the payload at send time and POSTs it with a service token (§2), retrying with back-off while the hub is down, so a user action never fails because the hub is offline. Intents are kept per hub (prod and dev have separate registries).

No patient names (D4, A6). The deployed datasets' patient_name is a pseudonym code in most deploys (CA_P0043), but a real romanized or Korean name in 14 data versions (MR_Brachy, Prostate, MR_Prostate, ProstateCTV, GTV_MR_Cervical, …). Their image file names often embed it too (955 of 1,490 such items). Every deploy reply therefore drops the patient_name field. It also replaces any key or string that contains a known real name with a stable redacted:<12 hex> token, so the same image still joins across replies (data list, demographics, metrics detail). Pseudonym codes such as patient_id are kept. A real name is one with no digit, or one in Hangul. The names are read from /mnt/deploy/data/*/*/train_valid_dict.json and held only in the server's memory; they are never written to a cache file. openapi.json says so in info.description and x-redacted-fields. The :5000 pages are unchanged.

Rules every endpoint follows (app/api/deploy.py). The acting role is X-Hub-Role, checked like the page's role_required (admin passes everywhere), and never higher than the role of the token itself: the hub signs sub=user:<name> with the user's hub role, so a viewer's token cannot claim admin, and a dev-hub token stays general (§8.2, D60). X-Hub-User must be the token's user. An app: token must send both headers (400 otherwise); a logged-in :5000 session needs no headers. Replies: 401 without a valid token, 403 {ok:false, detail:"role"}, and unknown paths and methods answer JSON (404/405), never the site's HTML error page. Every write (non-GET) leaves an audit_logs row deploy_api <METHOD> <path> by=hub:<user> role=<role> status=<code>, a write refused for its role (403) too (A14b). The hub's anonymous 배포 tabs come as X-Hub-User: public, X-Hub-Role: general with the service token (§72.3–72.4, D321): they read what general reads, are refused anything above it, and get no account of their own (by = hub:public; pinned by PublicPrincipalTests). File paths in replies (download_path, download_paths) are relative to /api/v1/deploy/, so the hub URL is /ui/api/deploy/<path>. openapi.json is the plain OpenAPI document (no ok wrapper). Its x-sha256 hashes the document without x-sha256 and x-app-version, so it changes only when an endpoint or a shape changes (the hub's banner), not on every commit. It is also sent in the X-OpenAPI-SHA256 header, and the endpoint accepts a token without the X-Hub-* headers.

Latency and slow reads: replies come from the pages' stale-while-revalidate caches (warm: ≤ 3 s; /spec/profile/all ≈ 3 MB of JSON, gzip on). The first computation of something nobody opened before can take longer than the proxy's 30 s JSON timeout (a new /spec/compare pair took ≈ 45 s on dev; the page itself takes as long). Every read that can be slow is marked x-async: true in openapi.json: /dashboard, /models, the A2 GET reads above and the heavier A3 reads (/packaging, /config, /roi, /roi/best-metrics, …), never file downloads. It runs in the background and answers as usual if it finishes within 20 s; otherwise it answers 202 {ok:true, job_id, state:"running", progress_path:"jobs/{id}"}. GET /jobs/{id} → {state: running|done|error, path, status, result}, where result is the endpoint's normal reply. The job is kept 10 min after it ends, and only its user (or an admin) sees it. Identical calls while one runs share the job, and once it has finished the same call is fast and answers 200.

Releases: immutable packages, the new-release wizard's API, Jira, downloads (§77, v1.61, U152)

A package is a folder /mnt/deploy/release/<version>/ that never changes once written (D331). Every change, config, model or OD, becomes a new folder written by app/packaging/releases.py, the only writer there. The copy of a Config 관리 tag into an existing bundle (config_manager._deploy_to_release, the cause of D317) is gone: a tag registered in Config 관리 alone changes no bundle. Each new folder carries RELEASE.json with its state: candidate → released → superseded, or withdrawn. A folder without the file (every package before 2026-11-05) is released. Latest is the highest released standard package (x.y.z or the fix x.y.z.n, compared by their numbers) on the dashboard (hero and LATEST badge), in /downloads, in /models released_in, and in the hub registration (D333). 1.7.0.3, made by hand on 2026-11-03, got its RELEASE.json as a candidate (base 1.7.0, fix, changes computed against 1.7.0: 40 renames, no ROI added), so 1.7.0 stays latest until QA marks 1.7.0.3 released.

The flow (all under /api/v1/deploy/releases; guide: release flow). (1) POST uploads opens a staging area instance/packaging_workspace/release_uploads/<id>/. It expires after 24 h; a sweeper runs at start and hourly. (2) PUT uploads/{id}/files/{path}, once per file of the person's folder (raw body, ≤ 2 GiB, sha256 on the way). The path is recognised as config (the four JSON files), od (od_ct/od_mr.torchscript), model_weights / model_fingerprint (<Family>/3d_final_model.pt, <Family>/global_fingerprint.json), or ignored (recorded, never used). (3) analyze compares base + upload with the base. Per config file it gives the Config 관리 entry-level diff; per uploaded family new / changed / unchanged with md5 (identical weights are recognised by md5, the model version by the catalog's weights, never by git_tag) and the classes added or removed. It also gives a summary. ROI names are compared through the new presets' alternative_names, so a rename that keeps the old name as an alias is rois_renamed, not a removal plus an addition. Then the proposal (D332): any ROI new to the bundle (a preset or a fingerprint class) → patch x.y.(z+1); otherwise → fix x.y.z.(n+1), with n counted over the folders and the config tags; minor x.(y+1).0 only when the person ticks major. (4) create checks the rules synchronously, then runs as a job. It writes the new folder, hardlinking the base's weights and config files as 새 패키지 does: uploaded files are copied over them, and each fingerprint's version becomes the package version. It writes RELEASE.json (candidate) and RELEASE_NOTES.md. Then config/ gets the six files with a commit of those paths only, the annotated tag v<version> (message = summary, change lines, tickets; author = the hub user) and a best-effort push. Last, the outbox queues POST /svc/v1/releases. A failure moves the partial folder to /mnt/deploy/trash/release_<v>_failed_<ts>. The base folder is never written. (5) state: released needs a QA pass. It turns every older released standard package superseded (a legacy folder gets its RELEASE.json then), re-registers each changed folder, fills the QA section of the generated notes, and posts one Jira comment per ticket. withdrawn of a released package gives the packages it superseded back their released state.

Jira (app/jira/client.py, D334): REST v3 with basic auth. JIRA_SITE, JIRA_EMAIL, JIRA_API_TOKEN, JIRA_PROJECT and optional JIRA_READONLY come from the environment, else from ~/.config/aipipeline/env (or JIRA_ENV_FILE). The token is only ever in the Authorization header, never in a log line, an error text, a reply or a fixture. Jira answers a wrong login as an anonymous user (an empty search, not a 401), so every read first checks /rest/api/3/myself (cached 5 min). Ticket reads are cached 5 min. Any failure becomes unavailable: "jira_auth" | "jira_unreachable" | "jira_http_<n>" with the keys as plain links; it never fails a release or answers 5xx. JIRA_READONLY=1 (the dev instance) reads live but only logs the comment (jira comment (readonly) KEY: …).

What can go wrong

The first /spec page after a restart is slowAggregates are cached (memory, then data/*_cache.json) and refreshed in the background; the first build after a restart or on a fresh dev instance reads ~1200 files over NFS (tens of seconds to minutes). Later loads are instant; a number may lag one refresh after result files change.
Odd numbers → suspect the data firstWrong channel names in a fingerprint, a collapsed deployed data version, or a leaked validation split explain most surprises (e.g. MR_HNN 2.1.0 swapped Midbrain/Medulla, flagged as a channel-swap suspect). Check labels, bundle metadata and aggregation before blaming the model.
Outbox shows pending 404ssplits/meta and validation intents answered 404 no split of … with file_sha256 wait until the hub registers that split; they converge by themselves. Only failed intents (400/413/422) need a person (hub_register.py retry-failed after the fix).
Evaluation cannot start"all cases leaked", a hidden model version, less than 12 GB free memory, or the GPU lock held by training — the queue page says which.
External sources are read-onlyNotion (release notes) and Google Sheets (ROI viewer, certification) are only read; the central PACS index is only queried for DICOM headers.
